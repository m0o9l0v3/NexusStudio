## 手順と結果

`.github/scripts/verify-studio-pg17-db-roles.sh` を2つのクライアントで1回ずつ実行し、どちらも全項目成功（終了コード0）。検査した項目：

1. NexusInfra baseline（01-roles 相当）より前は、role・schema を作らずに失敗する
2. 誤ったクラスタ識別子、承認フラグの無い `production` を DDL の前に拒否する
3. 正しい対象で1回だけ作成でき、2回目は拒否される。2つの role は superuser・CREATEDB・CREATEROLE・REPLICATION・BYPASSRLS を持たない
4. migrator は `CREATE SCHEMA` を拒否される（DB の CREATE なし）。全移行を適用でき、再適用も冪等。`studio` の全オブジェクトの所有者は migrator
5. `grant-studio-runtime.sql` を2回適用できる。runtime は表の読み書きができ、DDL・移行履歴の読み取り・`public` の読み取り・migrator への `SET ROLE`・`CREATE ROLE` は拒否
6. ID 予約表は runtime から INSERT だけでき、UPDATE・DELETE・TRUNCATE は拒否
7. migrator は `public` に表を作れない。`nexus_public` は `studio` を読めない

事前検査の単体テスト（`tests/test_setup_studio_roles_pg17.py`）は 18.x・16.x・別DB・別ユーザー・非superuser・別識別子・PG18用の承認フラグを DDL の前に拒否することを確認した。PG18用の `tests/test_setup_studio_roles.py` も引き続き合格。

検証後、コンテナ・network・volume は個別に削除した。
