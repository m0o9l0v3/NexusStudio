## 1. 背景

E2-5 O-3c は、改名を「新しい ID の発行・旧 ID の廃止・参照の移行」を1つのトランザクションで行う操作と定め、v1.0 では Studio の画面に置かずレビュー済みの管理コマンドで行うとした（R2）。alias の解決先は追記で更新する（T2）。一方、Spot の位置は同じ ID の地図の目的地Featureから得る（§5.4、29 M1-D4）ため、Spot だけを改名しても、地図に新しい ID の目的地が無ければ公開できない。地図側の扱いと改名の対象範囲は E2-5 からは決まらない。

## 2. 決定事項

| # | 論点 | 決定 | 補足 |
|---|---|---|---|
| D1 | v1 で改名できる対象 | **公開中の Spot と、同じ ID の目的地Featureだけ。** ノード・階・通路など Spot 以外の ID の改名は、必要になったときに別途足す | 利用者決定。地図内の参照（`access_node_id`・`floor_id` 等）の書き換えを伴う改名は扱わない |
| D2 | 改名後の地図の用意 | **取り込み済みの下書きの版を指定する。** 目的地の ID を新しい ID に替えた地図を `map import` で取り込み、`--map-version` で渡す。コマンドは地図を生成・書き換えしない。指定できるのは最後に取り込んだ版だけ（地図の公開と同じ。31 D1） | 利用者決定。地図の中身は人が用意してレビューする（31 D1 と同じ経路） |
| D3 | 1つの Release に含めるもの | 地図の版の公開、新しい ID の Spot の公開（旧 Spot の公開中の内容を写す）、旧 Spot の取り下げ、旧 ID を会場にする公開中のイベントの公開し直し、予約表への追記、bundle の作り直し | 検証は通常の公開と同じ検証器。公開阻止があれば何も変えない。旧 Spot が新規選択停止でも、改名で旧 ID から替えた会場は新たな選択とみなさない（新しい ID は選択停止のまま写す） |
| D4 | 予約表への追記 | 旧 ID を公開中のすべての種別（`spot` と目的地の種別）で `retired` にし、`旧 ID → 新 ID` の alias と、旧 ID を解決先にしていた alias の付け替え（T2）を追記する。登録元は `rename`、Release ID を記録する | 新しい ID は通常の公開と同じく `active` で登録する |
| D5 | 未公開の変更がある場合 | 旧 Spot、または旧 ID を会場にする公開中のイベントに未公開の変更があれば、**改名しない**（先に公開するか戻す） | 確認していない変更を改名に紛れて公開しないため。下書きだけのイベントは、会場を新しい ID にした下書きの版を作るだけで公開しない |
| D6 | 実行の形 | `--apply` が無い実行は確認だけで、トランザクションを取り消して何も残さない。`--admin` に有効な管理者を指定し、Release・操作ログ・新しい版の作成者に残す | 最初に使う前に隔離環境で試験する（E2-5 O-3c R2） |

## 3. 使い方

```sh
cd apps/studio-api
dotnet run -- map import --file <新しい ID の地図> --evidence <根拠の JSON>   # 版番号を控える
dotnet run -- spot rename --from <旧 ID> --to <新しい ID> --map-version <版> --admin <メールアドレス>            # 確認だけ
dotnet run -- spot rename --from <旧 ID> --to <新しい ID> --map-version <版> --admin <メールアドレス> --apply    # 改名
```

コマンドは次の場合に何もせず失敗する：旧 Spot が公開中でない、未公開の変更がある（D5）、新しい ID の Spot がすでにある、新しい ID が予約表にある（公開済み・廃止済み・alias）、指定した版が下書きでない、指定した版より新しい版が取り込まれている、その版に旧 ID と同じ種別の新しい ID の目的地が無い、その版にまだ旧 ID がある。

## 4. 後続

- Spot 以外の ID の改名・廃止の管理操作（D1 の範囲外）。必要になった時点で判断する。
- 本番で最初に使う前に、隔離環境（NexusInfra の PG17 baseline）で試験する。
