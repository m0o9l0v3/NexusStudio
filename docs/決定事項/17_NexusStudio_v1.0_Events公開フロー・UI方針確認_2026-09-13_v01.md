## 1. 今回確認された範囲

利用者から「全体的なUIの方針として捉えるならとても素晴らしいです」との確認を受けた。次をNexus Studio全体へ展開する基準として扱う。

- 左Sidebar、中央Workspace、必要時の右Inspector。
- 表・フォーム・地図を主役にした落ち着いた制作ツール。
- 薄灰Canvas、白Surface、濃紺本文、青の選択・主要操作、黄／赤／緑の状態用途。
- Noto Sans JP、4px基準の余白、過度に小さくしない操作対象。
- 保存、公開、検証、処理結果を一つの状態へ混ぜず、色と日本語ラベルで示す。
- 1440程度でも主要作業領域が成立し、1920では中央領域に余裕を持たせる。

この確認は、Events各項目の最終配置、公開フローの細部、他画面、本実装の承認を意味しない。

## 3. 公開確認画面の情報設計

### 左：公開対象と差分

- 対象を「イベント1件」「全開催枠・全会場」と明示。
- 対象Revisionと基準Releaseを表示。
- 共通情報、開催枠、参加方式、会場、終日の参照時間を差分の種類ごとに表示。
- 「公開中」と「公開候補」を横並びで比較。
- 架空のイベント・日時・Revision・Releaseは設計用サンプルと明示。

### 右：検証と関連する影響

- 公開阻止と警告を別集計し、検証対象が「保存済みイベント＋現在の公開データ」であることを表示。
- `mb_f2_cr_2a`、`mb_f2_cr_2b`は大文字小文字を保持し、公開中のSpot参照として表示。
- 終日枠は、同じ公開候補の開催情報`9/21 10:00–15:00`を参照する設計例。
- Map Data下書きに公開阻止があっても、現在公開中の地図・Spotを使うこのイベント公開には混ぜない。
- 未公開Spotなど必要な関連変更がある場合も、自動で公開対象へ追加しない。
- 最終操作を「このイベントを公開」と具体的に表示。

## 4. 公開結果の状態

| 状態 | UI上の意味 |
|---|---|
| 公開処理中 | 確認した候補を一度だけ反映中。操作IDから結果を追跡できる |
| 公開成功 | サーバー側で整合した新しい公開版が確定し取得可能 |
| 結果確認中 | 通信切断等により結果不明。同じ操作IDで実状態を照会し、成功・失敗を推測しない |
| 未反映の失敗 | 新しい公開版は作られず、直前の公開版と保存済み下書きを維持 |

公開成功画面には「全iOS端末への反映完了を意味しません」を独立した注意として表示した。端末は更新取得時にReleaseを検証して切り替え、オフライン端末が直前の保存版を使う場合があることを示す。

## 5. Prototype遷移

主経路：

`10:386 保存内容を確認`
→ `19:2 公開内容を確認`
→ `19:130 公開処理中`
→ `19:258 公開成功`
→ `11:178 Events一覧`

補助経路：

- 公開確認の「編集へ戻る」→`10:386`。
- 公開処理中の「通信切断状態を見る」→`19:386`。
- 結果確認中の「状態を再確認」→設計例として`19:258`。
- 未反映の失敗の「公開確認へ戻る」→`19:2`。

クリック領域と遷移先IDをFigma Plugin APIで再取得して確認した。主要操作は39〜44px高、公開ボタンは364×44px。小さなアイコンだけへ主要操作を依存させていない。

## 6. 確認結果

- `19:2`、`19:130`、`19:258`、`19:386`、`19:514`をスクリーンショットで確認。
- 1440×1024で文字切れ、主要要素の重なり、未完了Placeholderは見つからなかった。
- 画面内の文字はNoto Sans JPのRegular／Medium／Boldを継続使用。
- Figma上の公開表現はPrototypeであり、実公開・実端末反映の検証ではない。

## 7. 次の確認事項

今回の公開フローで利用者に確認してもらう主な点は次の3点。

1. 公開確認を「左に差分、右に検証・影響」とする配置。
2. 無関係な下書きの問題を「公開対象外」として見せる強さと文言。
3. 公開成功後に、端末反映を別状態として注意表示する情報量。

この範囲の確認後、同じUI基準をOverviewへ展開する。Overviewでは巨大KPIカードを避け、現在の公開版、開催情報、未公開変更、検証状況、最近の操作から次の作業を判断できる構成にする。
