## 1. 実装開始の判断

**開始できる：** 隔離した開発環境における「イベント1件を編集 → 複数枠・複数会場を設定 → 下書き保存 → 再表示」までの実装。既存の本番データ・本番APIに触れずに完結する。

**開始できない：** 本番公開とiOS配信。次の3点が外部要因で塞がっている。

| 阻止要因 | 内容 | 根拠 | 解ける条件 |
|---|---|---|---|
| **部屋canonical IDの契約が無い** | 建物・フロア・ノード・入口はE1-2で確定しSchemaにもあるが、部屋・教室には採用済み決定記録も公開Schema上の置き場所も無い。ID台帳は72件の部屋IDを持つが判定は`keep`75／`rename_now`24／`phase2_review`17／`deprecate`3が混在し、競合17件の多くが未解決 | 14 §5.4、N19、N20、S02 | 部屋IDの決定記録＋Schema v1.1 |
| **屋内・経路の実データが無い** | 変換CLIがblocker 7件で失敗する。フロア未登録、floor-local座標なし、アンカーなし、入口接続未確定、経路グラフ未作成 | 14 §5.6、N21 | #16／#36／#39 の実データ整備 |
| **iOSに取得・保存・版切替が無い** | `nexus-ios` に `URLSession`／`UserDefaults`／`FileManager`／`CoreData`／`SwiftData` が0件。地図の配信経路そのものが存在しない（ナビは静的JSONのSingleton） | 14 §7.1-7.2、N14、N17 | 配信契約の確定とiOS実装 |

これらはStudio側の実装で解消できない。**したがって「編集できること」と「公開してよいこと」を工程として分け、前者から着手する。**

## 2. 実装着手前に必要な判断（最大3件）

本書の他の部分は、利用者の追加判断なしに進められる。次の3件だけは、先に決めないと後戻りが大きい。

### 判断1：Studioは新規プロダクトか、既存E7の実装体か

**背景（今回判明）：** 既存Nexusのv1.0スコープ正本 `docs/v1.0-scope.md` は `epic::E7` を「管理ポータルの認証とトークン保管、スポット・開催日・イベント・MapDatasetの管理、Dashboard・Logsの実API接続、validation・publish・rollback操作」と定義し、その担当を `apps/admin-web` / `apps/admin-api` としている（N22）。これはStudio v1.0の範囲とほぼ重なる。同文書は「個別Issueや既存コードだけを変更して本文書と矛盾した状態にしない」と定めている。

| 選択肢 | 内容 | 利点 | 欠点 |
|---|---|---|---|
| **A（推奨）StudioをE7の実装体とし、admin-webを置き換える** | Studio Webを `nexus-studio` リポジトリで開発し、v1.0-scope上は **E7の管理ポータルの実体がStudioである**と位置づける。admin-webはQR hidden beta・Dashboard・Logsの現行画面を残すか、段階的にStudioへ移す | スコープ正本と矛盾しない。API・DB・validator・配信の所有元が `nexus-mobile` に一本化される。E2（MapDataset publish/rollback＋iOS取得）とE7が同じ公開契約を共有できる | v1.0-scope.md と README の更新が必要（別途、利用者の判断記録として） |
| B 完全に別プロダクトとする | Studioが独自のAPI・DB・公開基盤を持つ | Studioの設計自由度が最大 | 公開・認証の責務が二重化する。同じDBを2系統が書く構成は部分反映と競合を生みやすい。E7が宙に浮く |
| C admin-webを拡張し、Studioリポジトリを使わない | 新規リポジトリを作らない | 移行コストが最小 | 承認済みのStudio UI方針（左Sidebar／Workspace／Inspector、落ち着いた配色）を、MUIとshadcnが混在した既存画面へ後付けすることになる。16〜20の設計資産が活きにくい |

**推奨はA。** 理由：Studioが必要とする公開・検証・復旧・配信は、すべて既存Nexus側の資産（MapDataset validator、Schema、canonical ID契約、public-api）と不可分である。所有元を分けると、同じ公開整合性を2箇所で実装することになる。

### 判断2：Studio用のDBを既存admin DBと同居させるか、分離するか

| 選択肢 | 内容 | 利点 | 欠点 |
|---|---|---|---|
| **A（推奨）同一PostgreSQLインスタンス内に `studio` schema を新設** | 既存の `public` schema（events / spots / oc_days ほか）はそのまま。Studioの編集・公開モデルは `studio` schema に置き、旧表は読み取りと明示的な移行のみ | 1つのトランザクションで公開を原子的に確定できる。バックアップ・復旧が1系統。個人運営の運用負荷が最小 | schema分離の運用規約が要る。マイグレーションの所有元を明確にする必要がある |
| B 別DBインスタンス | 完全分離 | 事故の影響範囲が狭い | 公開時に2相コミットが必要になる。「部分反映を作らない」という確定方針に対して実装が難しくなる |

**推奨はA。** 「選んだ変更をまとめて反映し、一部だけ公開された状態を作らない」（06 §5-6）は、単一トランザクションで満たすのが最も確実である。

### 判断3：.NET 8 のまま進めるか、.NET 10 LTS へ先に上げるか

**背景：** .NET 8 のサポート終了は **2026-11-10**（O09）。本書作成時点から約7週間後。既存 `admin-api` / `public-api` は `net8.0` 固定（N25）。

| 選択肢 | 内容 | 判断 |
|---|---|---|
| **A（推奨）Step 0 で .NET 10 LTS へ上げてから Studio の新規コードを書く** | 既存2プロジェクト＋2テストプロジェクトのTFMとEF Core／Npgsqlを更新し、CIを通す。Studioの新規APIは最初から .NET 10 上に載せる | 新規コードをサポート切れの土台に積まない。更新の影響範囲が最小の時期（新規コードが0の今）に行える |
| B .NET 8 のまま着手し、あとで上げる | 着手が数日早い | 新規コード量が増えてから上げることになる。11月以降はセキュリティ修正も受けられない |

**推奨はA。** ただしこれは「先にやる作業」であって「着手できない理由」ではない。Step 0 は Studio の画面実装と並行できる（Studio Web は .NET に依存しない）。

## 4. データ構造の契約案

以下はすべて**提案**である。フィールド名・型は実装時に確定する。

### 4.1 編集と公開の分離

3種類の行に分ける。

| 種別 | 役割 | 可変性 |
|---|---|---|
| **Revision** | ある時点の編集内容の完全なスナップショット（JSONB） | **不変**。保存のたびに新しい行 |
| **編集head** | 対象ごとに「現在の下書きRevision」を指す | 可変。楽観的排他制御の対象 |
| **Release** | 公開操作1回の結果。どのRevisionの組み合わせを公開したか | **不変** |

```
studio.event_heads        (event_id PK, current_revision_id, updated_at, updated_by, row_version)
studio.event_revisions    (revision_id PK, event_id, payload JSONB, created_at, created_by, base_revision_id)
studio.releases           (release_id PK, kind, created_at, created_by, operation_id UNIQUE,
                           status, message, superseded_by)
studio.release_entries    (release_id, target_kind, target_id, revision_id, action)   -- publish / withdraw / restore
studio.event_published    (event_id PK, release_id, revision_id, published_at)        -- 現在の公開版
```

要点：

- **`operation_id` に UNIQUE 制約を置く。** クライアントが発行したIDを受け取り、同じIDの再送は新しいReleaseを作らず既存の結果を返す。これで「連打・再試行で重複公開を作らない」「結果不明時に同じ操作IDで実状態を照会する」（06 §5-6、11 RL-13、17 §4）を制約レベルで満たす。現行コードには冪等性が一切無い（14 §6.2）。
- **`event_heads.row_version` を楽観的排他制御に使う。** 保存要求は読み込んだrow_versionを伴い、不一致なら409を返して入力を失わせない（12 UI-23、07 AC20）。
- **公開は単一トランザクション。** `releases` ＋ `release_entries` ＋ `event_published` を同時に書く。失敗すれば何も変わらない（06 §5-6）。
- 「未公開／公開中／公開中・未公開変更あり／取り下げ済み」は、`event_published` の有無と `current_revision_id` との一致で**算出する**。手入力の状態フィールドを持たない（07 §5）。

### 4.2 Event Revision の payload（案）

```jsonc
{
  "schemaVersion": "studio.event/1",
  "title": "…",
  "description": "…",
  "categoryId": "…",            // null 可（下書き）
  "occurrenceId": "…",          // 開催回ID。null 可（下書き）
  "imageRef": { "assetId": "…", "state": "ready|processing|failed" } | null,
  "slots": [
    {
      "slotId": "…",            // 安定ID。複製で新規発行、日時変更では維持（07 EV-32/33）
      "ocDayId": "…",           // 開催日ID。日付はここから決まる（08）
      "timeMode": "fixed" | "allDay",
      "fixed": { "start": "10:00", "end": "10:45" } | null,
      "participation": "atStart" | "anytime" | null,   // 終日でも自動設定しない（07 EV-42）
      "status": "normal" | "cancelled",                 // 枠独自の中止
      "cancelNote": "…" | null,
      "venues": [
        { "canonicalSpotId": "mb_f2_rm_2a", "note": "受付", "sortOrder": 0 }
      ]
    }
  ]
}
```

判断のポイント：

- **終日枠は実時刻を payload に焼き込まない。** `timeMode: "allDay"` と `ocDayId` だけを持ち、実際の開始・終了は**公開時に同一Release内で開催日の公開時間から解決する**。これにより「参照元だけを更新してイベントと食い違わせない」（07 §4.6、08 §5）が構造的に保証される。前版および07は「公開版に確認した時間と参照元の版を保持する」案だったが、本版では**参照として保持し、配信時に同一Releaseで解決する**簡素化を提案する（→7章 修正提案2）。
- **canonicalSpotId は文字列として厳密一致で保持する。** 小文字化・表示名からの生成・近傍置換をどの層でも行わない。既存 public-api の `ResolveSpotCode`（30 m近傍＋大文字小文字無視、N13）には**新データを一切通さない**。
- 日時はキャンパス現地時刻（JST）の `"HH:mm"` として保持し、UTC変換は配信時に行う。既存 `/api/events/today` も `"HH:mm"` 文字列で返しており（N13）、表示契約は揃う。

### 4.3 開催情報・カテゴリ・Spot・地図

| 対象 | 案 |
|---|---|
| 開催回 | `studio.occurrences(occurrence_id, name, …)`。Revision方式は Event と同じ |
| 開催日 | `studio.oc_days(oc_day_id, occurrence_id, date, public_start, public_end, status, cancel_note)`。**一意制約は `(occurrence_id, date)`**。既存 `oc_days.date` のグローバルUNIQUE（N06）は08の方針と衝突するため踏襲しない。既存表は互換読み取り用に残す |
| カテゴリ | `studio.categories(category_id, name, sort_order, selectable)`。**一覧全体で1つの公開単位**。`selectable=false` が「新規選択停止」。既存参照は維持する |
| Spot | 既存 `spots.code` を canonical ID の器として維持。属性（別名・種別・建物・階・座標系・出典・確認状態・利用状態）は `studio` schema 側の拡張表に持ち、Revision対象にする。**`utilization` は3値**（`available` / `noNewSelection` / `withdrawn`）とし、現行の bool `IsPublished`（N03）を置き換えない（併存させ、移行時に写像） |
| 地図 | 既存 `map_datasets`（version UNIQUE、status CHECK、checksum CHECK、N04）を**そのまま**地図の公開単位として使う。Studioは draft 行を作り、validator に通し、published へ遷移させる |
| alias | `spot_id_aliases(alias_code, spot_id, created_at, reason)` をE1-3の設計どおり新設。validator の `SpotAlias` 契約（N12）が既にこの形を前提にしている |

## 5. 主要APIの契約案

すべて `admin/studio/` 配下に置き、既存 `admin/events` などは触らない。**旧エンドポイントの保存処理を新画面から呼ばない。**

### 5.1 編集・保存

| メソッド | パス | 要求 | 応答・規則 |
|---|---|---|---|
| GET | `/admin/studio/events` | 検索・絞り込み・並べ替え | 一覧。各件に公開状態・保存状態・枠数・会場要約・更新日時 |
| GET | `/admin/studio/events/{id}` | — | 編集head Revision ＋ 公開中Revision ＋ `rowVersion` |
| POST | `/admin/studio/events` | payload | 新規下書き。空でも保存できる |
| PUT | `/admin/studio/events/{id}` | payload ＋ `rowVersion` | 新Revisionを作り head を進める。**rowVersion不一致は 409** と最新内容を返す（入力は失わせない） |
| POST | `/admin/studio/events/{id}/discard-unsaved` | — | 最後に保存したRevisionへ戻す（EV-27） |
| POST | `/admin/studio/events/{id}/discard-unpublished` | — | 公開中Revisionを新しい下書きheadにする（EV-28） |

**下書き保存は入力不足を拒否しない。** 拒否するのは「システムで扱えない入力」だけ（壊れた参照形式、不正な画像）。これは07 §6の確定方針。

### 5.2 検証

| メソッド | パス | 意味 |
|---|---|---|
| POST | `/admin/studio/validate/draft` | **全下書き診断**。管理者向け。ここでのエラーは無関係な公開を止めない |
| POST | `/admin/studio/validate/candidate` | **公開候補の検証**。「選んだ対象のRevision ＋ それ以外の現在の公開データ」で公開後の状態を組み立てて検証する |

応答は `{ blocking: [...], warnings: [...], info: [...], validatorStatus: "ok" | "failed" }`。**検証器自体の失敗を合格として返さない**（11 VA-10、RA-07）。各所見は対象ID・理由コード・問題値・期待条件・修正先（イベント／枠／会場行／地図地物）を持つ。

地図の検証は既存 `MapDatasetValidator.Validate(payload, context)` をそのまま呼ぶ。`DatasetValidationContext` の各項目（出発ノード、キャンパス許容範囲、ENU原点、許容値、期待所要秒、フロア変換証跡、DB Spotスナップショット、公開ナビID、alias、予約済みID）を**管理者が承認した値として保存し、渡す**。渡さなければ `missing_validation_context` で公開不可になる（N12）——これが「根拠不足を自動合格にしない」の実装である。

### 5.3 公開・取り下げ・復旧

| メソッド | パス | 要求 | 規則 |
|---|---|---|---|
| POST | `/admin/studio/releases` | `{ operationId, entries:[{targetKind,targetId,revisionId,action}], confirmedValidationId, message? }` | 単一トランザクション。`operationId` 重複は**既存結果を返す**（新規作成しない）。`confirmedValidationId` が指す検証以降に対象または関連公開データが変わっていたら **409 再確認要求**（06 §5-5、11 RA-04） |
| GET | `/admin/studio/releases/{operationId}` | — | **結果確認中**からの照会経路。成功・失敗を推測しない（17 §4） |
| GET | `/admin/studio/releases` | 絞り込み | 履歴一覧。版・操作・対象・実行者・日時・結果 |
| POST | `/admin/studio/releases/{id}/withdraw` | `{ operationId, targetId }` | 取り下げ。**下書きの入力不足を阻止理由にしない**（EV-25、11 §6） |
| POST | `/admin/studio/restore/preview` | `{ targetKind, targetId, revisionId }` | 復旧候補の差分と、現在の関連データでの再検証結果。**本番は変更しない** |
| POST | `/admin/studio/restore` | `{ operationId, targetKind, targetId, revisionId, confirmedValidationId }` | 現在の未公開下書きを**退避Revisionとして保存してから**、新しいReleaseとして反映（RL-12） |

`action` を `publish` / `withdraw` / `restore` の3種に絞り、公開処理の実体を**1つ**にする。取り下げも復旧も「新しいReleaseを作る」で表現する。過去へ巻き戻す別経路を作らない。

### 5.4 配信（public-api）

| メソッド | パス | 意味 |
|---|---|---|
| GET | `/api/v2/manifest` | 現在の公開一式：`{ releaseId, publishedAt, events:{version}, occurrences:{version}, categories:{version}, mapDataset:{version, checksum} }` |
| GET | `/api/v2/events?release={id}` | その版のイベント一式（枠・会場・時間方式・参加案内・中止を含む） |
| GET | `/api/v2/map-dataset?version={n}` | MapDataset payload。`checksum` で完全性を検証できる |

**端末は manifest を取り、一式を揃えてから切り替える。** 一部取得失敗時は直前の整合した保存版を使い続ける（11 §8、RA-11）。既存 `/api/events/today` は旧クライアント（`web/` LP、`apps/mobile-ios`）向けに**別経路として残す**。新データを旧DTOへ黙って切り詰めない（07 §8）。

2. 保存後に一覧へ戻り、同じイベントを開くと、枠の順序・会場の順序・会場補足・時間方式・参加案内が**1つも欠けずに再表示される**。

| 項目 | 完了条件 |
|---|---|
| 4-a | 全下書き診断と公開候補検証を**別経路**で実装。前者のエラーが後者を止めない（RA-01） |
| 4-b | 公開確認画面（左＝差分、右＝検証と関連影響）。17で承認済み |

| 4-e | 取り下げ・履歴・復旧（退避まで） |
| 4-f | 管理操作ログ（誰が・いつ・何を・結果） |

**障害試験（これを通らないと「公開機能が完成した」と言わない）：**

| 試験 | 期待 |
|---|---|
| 公開中にAPIプロセスを落とす | 新しい公開版が作られないか、完全に作られるかのどちらか。**中間状態が残らない** |
| 同じ `operationId` で2回送る | Releaseが1つだけ。2回目は同じ結果を返す |
| 公開ボタンを連打する | 同上 |
| 応答直前に通信を切る | 「結果確認中」を表示し、同じ operationId で照会して実状態が分かる |
| 検証後に対象Revisionを別タブで更新してから公開 | 409 再確認要求。古い確認結果で公開しない |
| 無関係な地図下書きにエラーがある状態でイベントを公開 | **公開できる**（RA-01、AC10） |
| 未公開Spotを会場に指定して公開 | 阻止し、理由と修正先を示す。Spotを自動公開しない（AC09、RA-02） |
| 検証サービスを意図的に失敗させる | 検証エラーとして公開を止める。合格と表示しない（RA-07） |

| 項目 | 内容 |
|---|---|

## 9. 地図編集の技術検証計画

**目的：** 採用候補（MapLibre GL JS ＋ Terra Draw）が、既存の正式データを壊さずに往復できることを確かめる。**製品実装ではなく技術ゲートである。**

### 9.1 前提となる設計

```
[ 編集正本（アプリのstate） ]  ← ここが唯一の真実
        │  編集対象のFeatureだけを渡す
        ▼
[ Terra Draw store ]  ← Point / LineString / Polygon のみ。穴とMultiPolygonは拒否
        │  変更イベント
        ▼
[ 編集正本へ反映 ] → [ 保存API ] → [ サーバー側 MapDatasetValidator ]

[ 道路・入口・ノード・経路・未対応地物 ] → MapLibre の別source/layerで表示のみ。Terra Drawへ渡さない
```

- **`Draw.getAll()` の結果で正本を上書きしない。** ライブラリのstoreはFeatureのみを表現し、FeatureCollection直下の `metadata` や `bbox` の完全保持を保証しない（O05）。
- 編集不可の地物は最初からライブラリに渡さない。渡さなければ壊れない。
- Undo／Redo はアプリ側の command 履歴で持つ。**本番公開を戻す機能ではない**（10 §5、MA-11）。

### 9.2 検証手順（代表建物での往復）

対象は `mb`（教室棟）と `ptb`（実習棟）。理由：確定版GeoJSONで `status: confirmed` が付いている**唯一の2棟**である（14 §5.2）。

| # | 手順 | 合格条件 |
|---|---|---|
| 1 | 確定版GeoJSON（S01）のコピーを検証環境に読み込む。**原本は変更しない** | 26地物すべてが表示される。道路・駐車場・ランドマーク・候補も描画される |
| 2 | `mb` を選択して頂点編集モードへ入る | `mb` の頂点だけがハンドル表示される。他の地物にハンドルが出ない |
| 3 | 頂点を1つ移動する | 形状が追従する。**他の地物が動かない** |
| 4 | 辺の中点から頂点を1つ追加する | 頂点数が1増える |
| 5 | 頂点を1つ削除する | 形状が成立する範囲で削除できる。成立しない場合は拒否する |
| 6 | Undo を3回、Redo を3回 | 開始前の形状に完全に戻り、再適用できる |
| 7 | 自己交差する形状を意図的に作る | 問題として表示され、**編集確定または保存が阻止される**（MV-01、MA-05）。Terra Drawの `ValidateNotSelfIntersecting` とサーバー側 `IsValid` の**両方**で検出されること |
| 8 | 編集を確定して保存する | 保存API経由で draft MapDataset が作られる |
| 9 | 画面を再読み込みして同じ draft を開く | **`mb` の編集結果が保持されている** |
| 10 | 保存結果と手順1のコピーを差分比較する | **`mb` の geometry 以外が1バイトも変わっていない。** 未編集の25地物、`metadata`、プロパティ、座標精度、環の向き、キー順が保持されている（ME-27、MV-08、MA-10） |
| 11 | 穴を持つPolygonとMultiPolygonの合成テストデータを読み込む | ライブラリが**拒否**し、その地物が編集不可であることが画面に表示される。**黙って単純化・消去しない**（MA-06、ME-26） |
| 12 | 参考背景（外部タイル）を無効にする | 正規データの編集が**継続できる**。背景取得失敗と正規データを区別して表示する（ME-25、MA-09） |

### 9.3 高さと3Dの扱い

**この検証では高さを編集しない。**

- 確定版GeoJSONにもMapDataset Schema v1にも、高さ・階数・出典の**保存先が存在しない**（14 §5.2、§5.5）。
- MapLibre の `fill-extrusion-height` は既定0 m（O03）なので、値を与えなければ平面として描画される。これが現時点の**正しい表示**である。
- 3D表示の確認が必要な場合は、**Preview専用の明示的な仮値**を使い、画面に「仮の表示用高さ（正式値ではない）」と表示し、**保存もAPI送信もしない**。仮値がpayloadへ入る経路をコードレベルで作らない。
- 高さ編集は、Schema v1.1 と正式値・出典が揃ってから着手する（修正提案7）。

**架空の高さを正式値として使わない** — この制約は検証コードにも適用する。テストfixtureに高さを入れる場合は、ファイル名と値に `sample_` 接頭辞を付け、本番経路へ混入しないことをテストで保証する。

### 9.4 性能の測定基準（先に決める）

未測定の件数・フレームレートを達成値として報告しない。測定前に次を決める。

| 項目 | 決めること |
|---|---|
| 代表データ量 | 現在26地物。経路グラフ導入後の想定ノード・辺数 |
| 最低PC | CPU・メモリ・GPUの下限 |
| 対象ブラウザ | 版を含めて指定 |
| 合格基準 | 初期描画時間、頂点ドラッグ中のフレームレート、保存の応答時間 |

### 9.5 この検証で分かること・分からないこと

| 分かる | 分からない |
|---|---|
| ライブラリが既存形状を壊さず往復できるか | 建物の形状が**現実と合っているか** |
| 未編集レイヤーが保持されるか | 入口・経路の接続が**正しいか** |
| 自己交差などの不正形状を止められるか | 高さ・階数の**正式値** |
| Undo／Redo が編集セッション内で成立するか | 実データ規模での性能 |

「ピン配置・輪郭編集・3D表示の成功だけで、入口や案内経路の正しさを証明しない」（00 §4-6）を検証レポートにも明記する。
