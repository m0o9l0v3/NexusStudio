## 2. この決定で確定したこと・新たに判明したこと

### 2.1 admin-webを捨てることで失うものは、実質的にほぼ無い

D-11の妥当性を確認するため、`apps/admin-web/src` の全画面を再確認した。結果は次のとおりで、**捨てる判断を裏付ける**。

| 画面 | ルーティング | データ源 | 失うもの |
|---|---|---|---|
| Dashboard（`/`） | あり | **ハードコード定数のみ**（`pages/Dashboard.tsx:6-30`）。API呼び出し0件 | なし（モック） |
| CrowdAnalysis（`/spots`） | あり | **ハードコード定数のみ**（`pages/CrowdAnalysis.tsx:5-25`） | なし（モック） |
| QRIssue（`/qr`） | あり | **ハードコード＋ローカルstateのみ**（`pages/QRIssue.tsx:19-22`） | なし（モック）。QRはv1.0の正式機能ではない |
| Logs（`/logs`） | あり | **ハードコード定数のみ**（`pages/Logs.tsx:5-9`） | なし（モック） |
| Events（`/events`） | あり | `<Placeholder>` | なし |
| Schedule / Settings | あり | `<Placeholder>` | なし |
| **EventsPage** | **なし（未ルーティング）** | **実API接続**（TanStack Query＋`api/admin.ts`） | 到達不能なため運用上は失うものなし |
| **EventQrIssuesPage** | **なし（未ルーティング）** | **実API接続** | 同上 |

`apiClient` / `useQuery` / `useMutation` を参照しているのは未ルーティングの2ファイルだけで、**利用者が実際に開ける画面には実データが1件も流れていない**。さらに `EventsPage` が遷移先とする `/events/new`・`/events/{id}/edit`・`/events/{id}/qr-issues` は `App.tsx` にルート定義が無く、`path="*"` で `/` へ転送される。

MUI と Tailwind／Radix が混在しているのは、この2世代のUIが同居しているためである。Studioでは**Radix＋Tailwindに統一し、MUIを持ち込まない**（v01 §3のとおり）。

### 2.2 唯一、内容として参考になるフロントエンド資産

`apps/admin-web/src/api/admin.ts`（200行）は、`packages/openapi/admin.yaml` から `openapi-typescript` で生成した型を使った薄いAPIラッパーである。**コードとしては移植しない**（対象APIがStudioでは別物になるため）が、**「版付きOpenAPI → 型生成 → 薄いラッパー → TanStack Query」という構成は、Studioでもそのまま採る**。これは資産の移植ではなく、手法の継承である。

### 2.3 admin-apiは、Studio移行後に大きく縮む

D-11により管理画面がStudioへ移ると、`apps/admin-api` に残る責務は次だけになる。

| 現行の責務 | 移行後 |
|---|---|
| 管理者認証（単一固定資格情報） | **廃止**。StudioのIdentityへ（N08） |
| spots / events / oc-days の CRUD | **廃止**。Studioの編集・公開モデルへ |
| MapDataset モデル・validator | **Studioへ移植**（§4） |
| QR issue / one-time code | **残す**（v1.0 hidden beta。`docs/v1.0-scope.md`が主要導線から外した状態の維持を求めている） |
| `admin/logs/recent`・監査チェーン検証 | **残す**（参加者ログ `visit_logs` の閲覧。Studioの管理操作ログとは別概念、14 §4） |

つまり **admin-api は「QR hidden beta ＋ 参加者ログ閲覧」だけのサービスに縮む。** これはD-11の論理的な帰結であり、追加の判断ではない。admin-apiを直ちに削除する必要はなく、Studioが各責務を引き取った時点で該当Controllerを無効化していく。

### 2.4 14（本日版）への訂正

調査中、14 §3.6 に事実誤りが1点あったため訂正した。旧記述は「admin-webのEventsページはPlaceholderで、CRUD画面は存在しない」としていたが、正しくは **「`EventsPage.tsx` / `EventQrIssuesPage.tsx` という実API接続済みの実装が存在するが、`App.tsx` から参照されておらず到達できない」** である。あわせて、routedな4画面がすべてモック固定値であることを根拠付きで追記し、根拠索引N16を更新した。

この訂正はD-11の判断を変えない。むしろ「到達できる画面に実データが流れていない」ことを明確にし、廃棄の妥当性を強める。

## 3. 決定後の構成

### 3.1 リポジトリと所有の境界

v01 §3.2 は「.NET API・DBモデル・OpenAPI正本は nexus-mobile が所有し、Studioリポジトリに複製しない」としていた。**D-11によりこれを改める。**

| 所有 | リポジトリ | 内容 |
|---|---|---|
| **Nexus Studio** | `gitlab.com/11h27m/nexusstudio`（ローカル：`/Users/m09/Desktop/アプリ開発/nexus-studio/nexusstudio`） | Studio Web（React＋TS＋Vite）／**Studio API（.NET 10）**／`studio` schema のDBモデルとマイグレーション／Studio OpenAPI／移植したMapDataset validator／Studioのテスト |
| **Nexus（既存）** | `gitlab.com/11h27m/nexus-mobile` | iOS（`apps/nexus-ios`・`apps/mobile-ios`）／`public-api`（参加者向け読み取り）／縮小後の`admin-api`（QR hidden beta・参加者ログ）／`tools/map-dataset`／`web/` LP／**ID・座標・Schemaの決定記録** |
| 対象外 | — | `apps/sensor-lab-ios/**`（全段階） |

**リポジトリ間の結合は「版付きの契約とそのhash」だけにする。** 具体的には次の3つ。

1. `docs/schemas/map-dataset-geojson-v1.schema.json`（およびv1.1）— Studioは**内容をpinしたコピーを埋め込み**、hashで同一性を確認する。現行admin-apiが `AdminApi.csproj:8` で`EmbeddedResource`として埋め込んでいるのと同じ方式。
2. `docs/decisions/E1-1〜E1-5` — canonical ID・階層ID・座標系の決定記録。**Studioはこれに従う側であり、複製しない。**
3. Studio が公開する配信用OpenAPI（v2）— public-api と iOS が参照する。

隣のローカルフォルダを直接importする構成は製品へ入れない。

### 3.2 DBの境界（D-12）

同一PostgreSQLインスタンス、schemaで分離する。

| schema | 所有・書き込み | 読み取り |
|---|---|---|
| `studio` | **Studio API のみ** | Studio API、public-api（v2配信用・読み取り専用ロール） |
| `public`（既存 `events` / `spots` / `oc_days` / `map_datasets` / `qr_issues` / `visit_logs` ほか） | 縮小後のadmin-api（QR・ログ）。**events / spots / oc-days への書き込みは段階的に停止** | public-api（既存）、Studio API（移行期間の参照のみ） |

DBロールの分離は既存の方式を踏襲する。`public-api` には既に `PublicApiReadOnly` 接続文字列と専用ロールの導入手順（`docs/deploy-public-api-readonly-role.md`）があり、CIの `public-api-readonly-check` ジョブが `LogPersistenceService` 以外での `SaveChanges` を機械的に禁止している（14 §3.2）。**同じ考え方をStudioにも適用し、public-apiには `studio` schema への読み取り専用権限のみを与える。**

### 3.3 公開責務の二重化をどう避けるか

v01 §2でB案の欠点として挙げた「公開責務が二重化する／同じDBを2系統が書く」は、次の一本化規則で回避する。

> **規則：編集・公開の書き込みはStudio APIに一本化する。参加者向けの読み取りはpublic-apiに一本化する。**

| 操作 | 担当 | 根拠 |
|---|---|---|
| イベント・開催情報・カテゴリ・Spot・地図の編集と公開 | **Studio API のみ** | D-11 |
| 参加者向けの読み取り（iOS・LP） | **public-api のみ** | `docs/api-foundation.md` の責務境界（N23）。CIで担保済み |
| QR発行・ワンタイムコード・参加者ログ閲覧 | 縮小後の admin-api | v1.0-scope の hidden beta 方針 |

**Studio APIは参加者向けの配信エンドポイントを持たない。** これにより、`docs/api-foundation.md` が定める「admin＝書き込み、public＝参加者向け読み取り」の境界を、プロダクトが分かれても維持できる。iOSのベースURLも1つのままにできる。

### 3.4 旧読み取りモデルへの射影は「できる範囲だけ」

移行期間中、既存iOS・LPは `GET /api/events/today` 等で `public.events` を読み続ける。Studioで作ったイベントを旧クライアントにも見せたい場合、公開トランザクションの中で `public.events` へ射影する選択肢がある。ただし**構造的な上限がある**。

- `public.events` は**単一のStartsAt／EndsAt／LocationText**しか持たない（N01）。
- したがって **複数枠・複数会場のイベントは、旧形式へ損失なく射影できない。**

**規則：射影は「1枠1会場のイベント」に限る。複数枠・複数会場のイベントを旧形式の1枠1会場へ切り詰めて射影してはならない**（07 §8「複数会場を旧形式の1会場へ黙って切り詰めない」）。射影できないイベントは、v2配信とiOS対応が揃うまで**旧クライアントには出さない**。

この制約があるため、Studioの本格運用は §8 Step 5（v2配信＋iOS対応）とセットになる。

### Step 2：最初の到達点 — イベント1件の編集と下書き保存

**到達点：「イベント1件を編集 → 複数枠・複数会場を設定 → 下書き保存 → 一覧へ戻る → 再表示して同じ内容が出る」。**

対象・完了条件・検証方法は **v01 §8 Step 2 をそのまま適用する**（2-a〜2-i、完了条件1〜5、検証表）。配置先がStudioリポジトリと `studio` schema になる点だけ読み替える。

再掲すると、完了条件の中核は次の5つ。

1. 会場0件・カテゴリ未選択・参加案内未選択でも**下書き保存できる**。
2. 再表示で枠順・会場順・会場補足・時間方式・参加案内が**1つも欠けない**。
3. canonical IDが**保存前後で1文字も変わらない**（大文字小文字を含む）。
4. 2タブ同時保存で**無断上書きされず**409と最新内容が出る。
5. 通信を落とした保存で失敗が表示され**入力が残る**。

検証は「保存payloadと再取得payloadのJSON正規化バイト比較」を自動テストとして持つ。画面で「それらしく見える」ことを完了条件にしない。

### Step 3〜4：開催情報・カテゴリ・Spot／検証・公開・履歴・復旧

**v01 §8 Step 3・Step 4 をそのまま適用する。** 障害試験（プロセス停止・operationId重複・連打・通信切断・検証後の更新・無関係な地図エラー・未公開Spot・検証サービス失敗）の8項目は、公開機能の完成条件として維持する。

### 9.1 地図公開機構の二重開発を避ける整理案

調査の途中で既存側に MapDataset draft API が実装された（14 §12）。この状況で取れる選択肢は次の3つ。

| 案 | 内容 | 利点 | 欠点 |
|---|---|---|---|
| **A（推奨）既存側の #20 を止め、地図のpublish／rollbackはStudioで作る** | 既存側は #19（draft API）までで区切り、publish／rollback／配信はStudioの公開基盤（Release・operationId冪等・復旧）に統合する。#19までの成果はStudioへ移植する（§4.1） | D-11と整合する。公開・復旧の機構が1つになり、イベントと地図が**同じReleaseモデル**で扱える。決定文書11「Releaseは公開操作の履歴と、その結果として利用できるデータの組み合わせ」を素直に実装できる | 既存側の #20 の計画変更が要る |
| B 既存側で地図のpublish／rollbackまで作り、Studioはそれを呼ぶ | Studioは地図編集UIに徹する | 既存側の進行を止めない | 公開の原子性が2サービスにまたがる。「イベントと地図を整合する組み合わせで公開する」（11 §1）が難しくなる。D-11の「Studioがプロダクト」という位置づけとも合わない |
| C 両方で作る | — | なし | **採用しない。** 同じ公開・復旧を2箇所で保守することになる |

**推奨はA。** ただし既存側のIssue計画に関わるため、利用者の判断が要る。判断までの間、Studio側は §8 Step 0-e（validator移植）と Step 2（イベント編集）を進められる。これらは地図の公開機構に依存しない。

なお、**#19までの成果（draft API・版払い出し・checksum保存）はどの案でも無駄にならない**。A案では移植、B案では利用、C案でも参照になる。
