## 1. 結論

**隔離した開発環境で「イベント1件を編集 → 複数枠・複数会場を設定 → 下書き保存 → 再表示」までの実装は開始できる。本番公開・iOS配信の開始条件は満たしていない。**

前版の結論は今回の再調査でも覆らなかった。そのうえで、今回新たに次の5点が判明した。これらは実装順序と最初の判断事項に直接影響する。

1. **既存Nexusのv1.0スコープ正本に、Studioとほぼ同一の範囲が`epic::E7`として既に定義されている。** `docs/v1.0-scope.md`はE7を「管理ポータルの認証とトークン保管、スポット・開催日・イベント・MapDatasetの管理、Dashboard・Logsの実API接続、validation・publish・rollback操作」と規定し、その担当を`admin-web`／`admin-api`としている。Studioを別プロダクトとして立てるか、E7の実装体としてadmin-webを置き換えるかは、実装着手前に決めるべき統治上の判断である（→15の判断事項1）。
2. **Studioの決定文書とFigmaが一貫して使っているサンプルcanonical ID `mb_f2_cr_2a` は、正の資料であるID台帳が「悪い例」として明示している値である。** 正しい形は`mb_f2_rm_2a`。台帳のConflict RegisterはC-004として`mb_f2_cr_2b〜2g`を未解決の競合（教室`rm`と廊下`cor`が`cr`を共用）として登録している（→5.3）。
3. **教室・部屋レベルのcanonical IDには、採用済みの決定記録も、公開Schema上の置き場所も存在しない。** 建物・フロア・ノード・入口はE1-2で確定しSchemaにも定義があるが、部屋は「今後定義される」（E1-3）ままである。イベントの会場をcanonical IDで参照する要件は、この1点で本番公開を止める（→5.4）。
4. **既存コードに、楽観的排他制御・冪等キーが存在しない。** `IsConcurrencyToken` / `RowVersion` / `ETag` / `If-Match` / idempotency 相当の実装を`apps/`配下の`*.cs`全体に対して検索し、0件だった。公開方針が要求する「無断上書きの防止」「連打で重複公開を作らない」は、現行基盤の上に**新設**が必要である。（明示的トランザクションについては、調査時点のブランチでは0件だったが、その後 MapDataset draft API で1件導入された。**§12を参照**）
5. **.NET 8のサポート終了が2026-11-10**（確認日2026-09-22、公式サポートポリシー）で、本調査時点から約7週間後である。既存`admin-api`／`public-api`は`net8.0`固定であり、新機能を8系へ積み増す判断は短期でサポート外を生む。

再利用の中心は、前版と同じく次のとおりである。ASP.NET Core／EF Core／PostgreSQLのAPI基盤、React／TypeScript／Viteの管理Web資産、canonical IDと座標系の決定記録、**C#のMapDataset publish validator**、Node製のMapDataset変換CLI、SwiftUIの画面・取得境界・状態区別。新設が必要な中心は、下書きと公開版の分離、Release、選択公開、検証、履歴、復旧、管理者個別認証、そしてiOSの通信・保存・版切替である。

### 3.2 起動による副作用（重要）

`apps/admin-api/Program.cs:139-143` は、環境を問わず起動時に`DbSeeder.SeedAsync()`を実行する。

```
using (var scope = app.Services.CreateScope())
{
    var seeder = scope.ServiceProvider.GetRequiredService<DbSeeder>();
    await seeder.SeedAsync();
}
```

`apps/admin-api/Data/DbSeeder.cs:17-24` は、SQLiteなら`EnsureCreatedAsync()`、それ以外（PostgreSQL）なら**`MigrateAsync()`**を呼ぶ。つまり**本番DBに対してもマイグレーションが起動時に自動適用される**。続く`DbSeeder.cs:26-98`はSpots／Events／OcDaysのサンプル行を投入する。投入は`AnyAsync`ガード付きで加算のみ（既存行の削除・上書きはない）だが、`Spot`については`pc_room`／`ctc`／`vehicle_hangar`／`basic_training_room`／`hangar`、および`SPOT-001`／`SPOT-002`（東京の緯度経度）を条件付きで追加する。

**影響**：調査・検証のために既存admin-apiを起動すると、接続先DBのスキーマと行が変わり得る。本調査では起動していない。Studioの検証環境では、シード実行を環境変数で切り離すか、専用DBを用意する必要がある（→15）。

`public-api`側には同種の副作用はない。`apps/public-api/Program.cs`にseederはなく、CIの`public-api-readonly-check`ジョブ（`.gitlab-ci.yml:46-63`）が`LogPersistenceService`以外での`SaveChanges`呼び出しを機械的に禁止している。

### 4.1 既存の「会場推測」は採用できない

`apps/public-api/Controllers/EventsController.cs:66-100` の `ResolveSpotCode` は、イベントに紐づくSpotを次の順で**推測**する。

1. `LocationText`（自由入力の場所文字列）を Spot の `Code` と突き合わせる。比較は `StringComparer.OrdinalIgnoreCase`（`EventsController.cs:43`）。
2. 一致しなければ、イベントの`Lat`/`Lng`から**最も近い公開Spotを探し、30 m以内なら採用する**（`EventsController.cs:84-99`）。

これは製品方針および既存の決定記録の双方に反する。

- 製品方針「表示名・GUID・別のSpotへ置換しません」「大文字・小文字を保持します」に対し、**表示名相当の文字列からの解決**と**大文字小文字を無視した一致**を行っている。
- `docs/decisions/E1-3-spot-id-integration.md` は「現行の`NavigationController`が使用する`OrdinalIgnoreCase`は**移行対象**であり、canonical IDの比較規則には採用しない」と明記している。同じ問題が`public-api/Controllers/NavigationController.cs:27,46-47`にも残っている。
- 「近くの建物や道路へ自動吸着して正式位置・接続済みとしない」（決定文書09）に対し、30 m近傍探索は座標の近さだけで会場を確定している。

**Studioでは、会場は開催枠に明示保存したcanonical IDだけを正とし、この推測経路に依存しない。** 既存経路は旧イベントの互換読み取りとしてのみ残し、新データには適用しない。

### 5.5 座標・階・高さの契約

- 公開座標系は WGS 84（OGC CRS84）、2次元 `[longitude, latitude]`、小数6桁。`crs`メンバーと高度の第3要素は出力しない（`docs/e1-6-map-dataset-conversion.md`）。
- 屋内の floor-local XY → 局所ENU → WGS 84 の相似変換が `tools/map-dataset/src/transform.mjs` に実装済み。許容誤差はE1-5準拠：数値往復 各点 ≤0.05 m／fit残差 RMS ≤2.0 m かつ各点 ≤3.0 m／check誤差 各点 ≤3.0 m／6桁丸めの追加誤差 ≤0.10 m。同じ値が C# 側 `Services/MapValidation/MapDatasetValidator.cs:311-314` にも `limits = { .05, 2, 3, 3, .10 }` として入っている。

**再利用できるのは MapDataset の版・状態・チェックサムの器だけである。** `map_datasets` は `version` にUNIQUE索引、`status` に `draft/published/archived` のCHECK制約、`checksum` に64文字長のCHECK制約を持つ（`AdminDbContext.cs:122-139`）。これは「不変の公開版」を作るうえで素直に使える。ただし遷移を実行する操作も、同時に2つのpublishedを作らせない制約も、まだ無い。

### 8.3 推奨と、前版からの変更点

**推奨：MapLibre GL JS ＋ Terra Draw（公式 `terra-draw-maplibre-gl-adapter` 経由）。**

前版（2026-09-13）は Mapbox GL Draw を推奨候補とし、Terra Draw を「Multi系非対応と穴の拒否理由があるため無条件採用しない」代替としていた。今回、次の2点が判明したため推奨を入れ替える。

1. **Terra Draw は MapLibre 用の第一級Adapterを公式に提供している。** Mapbox GL Draw は Mapbox GL JS 向けであり、MapLibre と組む場合はクラス名・style の調整（互換shim）が要る。恒久的な互換負債を負わない構成を優先する。
2. **「穴とMultiPolygonを拒否する」ことは、この設計では欠点ではなく安全側の性質である。** 確定版GeoJSONには**MultiPolygonが0件、穴を持つPolygonも0件**であることを今回の静的検査で確認した（5.2）。そのうえで、編集の正本をライブラリの外に持ち、**編集対象のFeatureだけをTerra Drawへ渡す**構成にすれば、穴・MultiPolygon・未対応属性を持つ地物は最初からライブラリに触れない。決定文書10の ME-26（未対応形状の保護）・MA-06（穴や複数形状を無断で単純化・消去しない）は、「静かに壊す」より「明示的に拒否する」ほうが素直に満たせる。

**弱点と成立条件**：

- 将来 MultiPolygon や穴のある建物を**編集**対象にする場合、Terra Drawでは扱えない。その時点で、読み取り専用のまま属性だけ編集するか、描画ライブラリを差し替えるかの判断が要る。**Terra Drawのstoreを保存形式にしない**ことが、この差し替え余地を残す条件である。
- Terra Draw の各modeの実動作・穴の拒否挙動・大量Feature時の性能は**未検証**である。実データでの往復試験を実装着手時の技術ゲートとする（→15）。
- 自己交差以外のtopology検証（穴の包含関係、環の向き、退化）は**サーバー側で行う**。既存 `MapDatasetValidator` が NetTopologySuite 2.6.0 を使って `IsValid` ／ ring orientation ／ 座標精度 を検査しており（`MapDatasetValidator.cs:72-78`）、ここを正とする。
- ライブラリのpatch版は実装開始日に公式配布元と依存関係を確認し、lockfileへ固定する。

### 12.3 Studioにとっての意味

この実装は、Studioが必要とする地図公開基盤の**前半部分が既存側で作られ始めた**ことを意味する。とくに次の2点は、Studioが自前で設計するより流用する価値が高い。

1. **単調増加する版の払い出し**：全状態（draft/published/archived）を通した最大版＋1を Serializable トランザクションで確保し、一意制約違反・直列化失敗を `IsVersionAllocationConflict`（:134-142）で判定して **409で再試行を求める**。PostgreSQLとSQLiteの両方のエラーコードに対応している。
2. **payloadを再シリアライズしない保存**：受け取った文字列をそのまま保存し、そのUTF-8バイト列からSHA-256を計算する（:131-132）。空白・改行・日本語を含む入力と checksum の対応が保存前後で変わらない。決定文書10のME-26／MV-08（未対応データを壊さない）に直結する性質である。

**同時に、調整すべき事項が生じた。** 既存側は `epic::E2`（MapDataset の draft → validation → publish → rollback → 配信）を #17／#18／#19 と進めており、**#20 で publish／rollback に着手する見込みである**。一方、決定 D-11 により Studio が地図の編集・公開を担う。**同じ公開・復旧機構を2箇所で作らないための整理が必要**であり、これは15 v02 §9のリスクとして扱う。
