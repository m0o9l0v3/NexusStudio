# タイムスケジュール取り込みの実現性調査

- 作成日：2026-11-16（日本時間）。版：v01。
- 状態：**調査と提案のみ（未承認）**。実装はオーナーの判断の後に行う。本書の「推奨」「提案」は承認済みではない。
- 対象：学校が今使っているオープンキャンパスのタイムスケジュール（Excel。PDF でも配られる）を、Nexus Studio に取り込めるか。
- 調査の根拠：`origin/develop`（165d468、2026-11-16 時点）のソースと `docs/決定事項/`。入力の形式は、オーナーが提供した 2026-11-14 の実ファイルの説明と、担当者名を除いた抜粋だけを使った。**.xlsx の実物は見ていない。**

---

## 0. 結論（先に）

1. **取り込みは実現できる。** タイムスケジュールの1行は、Studio の「イベント（1件）＋開催枠（1つ）」にほぼそのまま対応する。下書きの保存は入力不足でも通るため（`Events/EventDraft.cs` の方針、07 §6）、**地図が無い今でも、取り込んで下書きを作るところまでは今の仕組みで可能**。
2. **アプリに出す（公開する）には、今の規則では地図が要る。** イベントの公開には「会場（Spot）が公開済み」が要り、Spot の公開には「公開済みの地図にその場所がある」が要る（`Publishing/CandidateValidator.cs` の `venue_spot_unpublished`・`spot_map_unpublished`・`undefined_spot_canonical_id`）。取り込みはこの制約を変えない。
3. **公開に必要で、タイムスケジュールに無い情報がある。** イベントの「説明」と「カテゴリ」（必須。`description_required`・`category_required`）。毎回同じ名前の予定（学科説明・ドローン体験など）が多いので、**「予定名の対応表」で前回の説明・カテゴリを引き継ぐ**のが現実的。
4. **推奨：取り込みの中心（行の読み取り→分類→場所の対応→差分→下書き保存）を1つ作り、入口を2段階で増やす。** 第1段階は「Excel からコピーして貼り付け」、第2段階は「.xlsx ファイルを選ぶ」。PDF は読まない。
5. **担当者名は取り込みの入口で捨てる。** 貼り付けの場合は、名前の列をブラウザの中で捨ててからサーバーへ送るため、名前がサーバーに届かない。

---

## 1. 前提：なぜ取り込みか

先生方の働き方は変えない（Excel で作り、PDF にして配り、直前まで何度も直す。手元の見本はファイル名の末尾が「(13)」）。Nexus への入力を先生方にお願いすることはせず、オーナーか広報の担当者1人が、配られたファイルを Studio に入れる。取り込みはこの運用を成り立たせるための中心の機能である。

## 2. 調査で判明した事実：Studio の今のモデル

### 2.1 データの単位

| 単位 | 実体 | 主な項目 | 根拠 |
|---|---|---|---|
| 開催回 | `Occurrence` | 名称・出典メモ（`SourceNote`）・開催日の一覧 | `Models/ReferenceData.cs` |
| 開催日 | `OcDay` | 日付・一般公開時間（1日1区間。未登録は null のまま、推定しない）・中止 | 同上 |
| カテゴリ | `Category` | 名称・並び順・新規選択可否。一覧全体で1つの編集単位 | 同上 |
| Spot（場所） | `Spot` | canonical ID（厳密一致・生成しない）・名称・検索用の別名（`NameAliases`）・種別・説明 | 同上 |
| イベント | `EventHead`＋`EventRevision`（`studio.event/1`） | タイトル・説明・カテゴリ・開催回・開催枠の一覧 | `Models/EventRecords.cs`、`Events/EventDraft.cs` |
| 開催枠 | `EventSlot` | 安定した SlotId・開催日・時間方式（時間指定／終日）・開始/終了（"HH:mm"）・参加案内（開始時刻に集合／随時）・中止・会場の一覧 | `Events/EventDraft.cs` |
| 会場 | `SlotVenue` | Spot の canonical ID・補足 | 同上 |

保存は `operationId`（再送で重複しない）と `rowVersion`（競合したら上書きしない）で守られ、保存のたびに不変の Revision が残る。公開は Release で、**1回の公開に複数の対象（イベント・Spot・開催回など）をまとめて入れられる**（`Publishing/ReleaseEndpoints.cs` の `PublishRequest.Entries`）。

### 2.2 下書きで拒否されるもの（保存できない）

「システムで扱えない入力」だけ：タイトル500字超、開催枠200件超、時刻が "HH:mm" でない、同じ枠に同じ会場が2回、など（`EventDraftRules.Validate`）。**会場が空・説明が空・カテゴリ未選択でも下書きは保存できる。**

### 2.3 公開で止まるもの（イベント）

`CandidateValidator.ValidateEvent` より：タイトル・説明・カテゴリ・開催回が必須、カテゴリと開催回が公開済み、開催枠が1つ以上、各枠に開催日・時間方式・参加案内・開始と終了（開始＜終了）・会場1つ以上、会場の Spot が存在し公開済み・取り下げ済みでない・新規選択停止でない。一般公開時間の外・過去の日付は警告（止めない）。

Spot の公開は「地図が公開されている」「公開中の地図にその ID の目的地がある」「種別が設定済み」を要求する（`ValidateSpot`）。つまり**会場 → 公開済み Spot → 公開済み地図**の順に依存する（first-bundle-publish の調査結果と同じ）。

### 2.4 既にある場所の情報

- 実データの Spot 86件（`deploy/reference/spots.json`、決定事項34）。教室棟2階の教室には `2A`〜`2G` の別名が既に付いている（例：`mb_2f_cl_001`「2A教室」）。
- 見本に出てくる場所の候補：`2A` → `mb_2f_cl_001`（2A教室）、`CTC2` → `ctc2`（建物）、`PC教室` → `mb_2f_rm_003`（PC室）**かどうかは未確認**、食堂 → `dh`、寮 → `amh`／`lbh`。

### 2.5 地図が無い今、できること・できないこと

| 段階 | 地図なしで | 備考 |
|---|---|---|
| 取り込んで、イベントの下書きを作る | **できる** | 会場が未確定でも保存できる |
| 会場に canonical ID を入れる | できる（Spot 行があれば） | 本番に Spot 行があるかは `reference import` の実行次第 |
| 開催回・カテゴリを公開する | できる | |
| イベントを公開してアプリに出す | **できない** | 会場の Spot が公開できないため。規則を変えるのは別の判断（first-bundle-publish の選択肢 A/B/C） |
| 公開前の確認で「何が足りないか」を見る | できる | Validation 画面（全下書き診断）で一覧できる |

## 3. 入力の形式（2026-11-14 の実ファイルの説明から）

- シートは1枚、題は「2026年 11月 AM versionタイムスケジュール」。**日にちは題に無い**（年と月だけ）。
- 列：時間（開始。赤字のことがある）／所要時間（例「30分」。空欄あり）／内容（予定名。1行が結合セル内で2つ「学生生活 / 座談会」に分かれる）／特記（場所またはメモ：PC教室・2A・CTC2・参加者・支援学生用バス）／メイン担当（担当者名）。
- 行は種類ごとに色分け。スタッフだけの行（支援学生用バス・朝MTG）、移動の行、バス出発の行がある。
- 表の外に赤字の注記（※食堂ポット）。表の下に「プログラムごとの担当者」の一覧。
- AM版とPM版がありうる。

見本の中だけでも、そのまま機械的に変換できない点がある：

- 13:00 の「座談会・アンケート」は30分（〜13:30）だが、13:20 に「移動」、13:30 に帰りのバスがある（時間が重なる）。
- 寮見学・食堂でごはん・座談会・アンケートは特記が空（場所が書かれていない）。
- 最初のバスは「千歳駅」発で、キャンパスの Spot ではない。

## 4. 対応表：タイムスケジュール → Studio

| タイムスケジュール | Studio | 方法 | 確認画面で |
|---|---|---|---|
| シートの題（年・月・AM/PM） | 開催回・開催日 | **自動では決めない**。取り込み画面で開催回と開催日を選ぶ（題の年月は候補の絞り込みにだけ使う） | 選んだ日を大きく表示 |
| 時間 | 開催枠の開始（`fixed.start`） | "9:10"・"９：１０"・"9時10分"・Excel の時刻値を "HH:mm" にそろえる | 読めない時刻は赤で示し、保存させない |
| 所要時間 | 開催枠の終了（開始＋所要時間） | "30分"・"1時間"・"1時間30分" を読む。**空欄は空のまま**（推定しない） | 空欄の行に［次の予定の開始までにする］を出し、押したときだけ埋める |
| 内容 | イベントのタイトル | 前後の空白を除く。結合セルの「学生生活 / 座談会」は、確認画面で［1件にまとめる］［2件に分ける］を選ぶ | |
| 内容（予定名） | カテゴリ・説明・参加案内 | 「予定名の対応表」（§6）で前回の値を引き継ぐ | 引き継いだ値は「前回から」と示す |
| 特記（場所） | 会場（Spot の canonical ID） | 「場所の対応表」（§5）で引く | 分からない場所は「場所が決まっていません」 |
| 特記（場所以外。参加者など） | 使わない | 分類の手がかりにだけ使う（§7） | 行の横に原文を薄く表示 |
| 色・赤字 | 使わない（手がかりのみ） | 第2段階（.xlsx）で分類の候補に使う | |
| メイン担当 | **取り込まない** | 入口で捨てる（§9） | 列そのものを表示しない |
| 表の下の担当者一覧 | **取り込まない** | 表の終わり（最初の空行）以降を読まない | |
| 表の外の注記（※食堂ポット） | 使わない | 読まない | |
| — | 時間方式 | 常に「時間指定」 | |
| — | 開催枠の状態 | 常に「通常」（中止は Studio の画面で） | |

**1行＝1イベント＋1開催枠**を基本にする。AM版とPM版に同じ名前の予定がある場合に「1つのイベントに2つの枠」とするか「別々のイベント」とするかは、アプリでの見え方が変わるため**オーナーの判断が要る**（§13 の D1）。

## 5. 場所の対応表（特記 → Spot）

### 提案

- Studio に、取り込み専用の「場所の対応表」を新しく持つ（例：`studio.schedule_place_aliases`。項目は「書き方（原文）」「行き先」「最後に使った日」）。行き先は次のどれか：
  - Spot（canonical ID）
  - 「場所ではない」（参加者・支援学生用バス など。分類の手がかりとして使う）
- **Spot の「検索用の別名」（`NameAliases`）とは分ける。** 別名は参加者向けアプリの検索に出る（`ParticipantBundleProjection` の `search_aliases`）ため、「PC教室」のような学内の呼び方を勝手に増やすと、公開の内容が変わってしまう。ただし対応表で見つからないときは、Spot の名称と別名の**完全一致**を候補として出す（例：`2A` は既存の別名で `mb_2f_cl_001` が候補になる）。
- 比較は、前後の空白と全角/半角の英数字だけをそろえて行う。**canonical ID を作ったり推測したりはしない**（CLAUDE.md）。候補の提示とオーナーの選択だけ。
- 対応表は、取り込みの確認画面で場所を選んだときに［次回もこの場所にする］で増える。別に管理画面を作るのは後でよい（第3段階）。

### 分からない場所の扱い

- **取り込みは止めない。** その行の会場を空のまま下書きにし、確認画面と結果に「場所が決まっていません：PC教室（3件）」と出す。
- 公開しようとすると、今の検証（`slot_venue_required`）が止める。どれが足りないかは Validation 画面で一覧できる。
- 1つの書き方が複数の Spot に当たりそうなとき（例「CTC」と「CTC2」）は、自動で選ばず、候補を並べて選んでもらう。

## 6. 予定名の対応表（内容 → カテゴリ・説明）

タイムスケジュールにはイベントの説明とカテゴリが無いが、どちらも公開に必須である。毎回ほぼ同じ予定（学科説明・学生生活・座談会・ドローン体験・CATIA体験・寮見学・食堂）が並ぶので、**予定名ごとにカテゴリ・説明・参加案内・いつもの場所を覚えておき、次の取り込みで引き継ぐ**。

- 初回はオーナーが Studio でカテゴリと説明を入れる。2回目以降は引き継ぐ。
- 「場所が書いていない予定」（寮見学・食堂）は、ここに「いつもの場所」（例：食堂 → `dh`）を持たせて補う。確認画面では「いつもの場所」と示す。
- 引き継いだ値は下書きに入るだけで、公開前に見直せる。

## 7. 行の分類

| 分類 | 例 | 取り込み後 |
|---|---|---|
| 参加者向けの予定 | 学科説明、ドローン体験、寮見学 | イベントの下書きにする |
| 移動 | 移動 | 取り込まない（アプリでは予定の間の空き時間として見える） |
| バス | 参加者バス（千歳駅発）、帰りのバス | **v1 では取り込まない**（キャンパス外の場所は Spot にできず、会場が要る今の規則では公開できない）。扱いはオーナーの判断（§13 の D2） |
| スタッフだけ | 支援学生用バス、朝MTG | 取り込まない |
| 対象外 | 注記、空行、担当者一覧 | 読まない |

**規則で候補を出し、オーナーが確認画面で確定する**方式にする：

- 内容が「移動」 → 移動。
- 内容か特記に「バス」 → バス。特記の「支援学生用」「スタッフ」や、内容の「MTG」「打合せ」 → スタッフだけ。
- 特記が場所の対応表で「場所ではない（スタッフ）」になっている → スタッフだけ。
- 行の色（第2段階）→ その色で前回オーナーが選んだ分類を候補にする（色の意味を決め打ちしない）。
- どれにも当たらない → 参加者向けの予定（候補）。

確認画面では行ごとに分類を切り替えられ、変えた結果は次回の候補に使う（予定名の対応表に「いつもの分類」を持つ）。**スタッフだけの行が誤って公開される事故を防ぐため、「参加者向け」にした行は件数を確定ボタンの横に出す**（例「参加者向け 9件を下書きにします」）。

## 8. 何度も取り込み直すとき（版の差分）

### 8.1 方針

- 取り込みは**いつも下書きを作るだけ**で、公開はしない。公開は今の公開確認（差分表示と検証）を通す。これで「公開中の内容が途中の状態になる」ことは起きない：1回の公開は1つの Release にまとまり、まとめて切り替わる。
- (14) を取り込むと、(13) で作ったイベントを**更新**し、重複して作らない。

### 8.2 同じ予定かどうかの判定

取り込んだ行と Studio のイベントのつながりを記録する（例：`studio.schedule_import_links`：開催回・開催日・取り込みキー → イベントID・SlotId）。次の取り込みでは：

1. 同じ開催日で**予定名が同じ**行 → 同じイベント（同名が複数あるときは時刻の順で対応）。
2. 予定名は違うが、**時刻と場所が同じ**行 → 「名前が変わった同じ予定？」として候補を出し、オーナーが選ぶ。
3. どちらでもない → 新しい予定。
4. 前回あって今回無い → 「消えた予定」。**自動では消さない。** 確認画面で［残す］［この枠を中止にする］を選ぶ（公開中なら、中止にして公開すればアプリに「中止」と出る）。

SlotId はそのまま使い続ける（日時の変更では SlotId を維持する：07 EV-32/33）。

### 8.3 どの項目を取り込みで上書きするか

| 項目 | 取り込みで上書き | 理由 |
|---|---|---|
| 開始・終了時刻、会場、タイトル | する | 先生方のファイルが正 |
| 説明・カテゴリ・参加案内 | **しない**（新規のときだけ予定名の対応表から入れる） | Studio 側で整えた内容を消さない |
| 中止 | しない（「消えた予定」の選択だけ） | |

前回の取り込みの後に、Studio の画面で「上書きする項目」を直していた場合は、確認画面で「Studio で直した内容があります：開始 10:00 → ファイルでは 10:05」と出し、どちらにするか選んでもらう。

### 8.4 確認画面での差分の見せ方

「新しく増える 1件」「時間が変わる 2件」「場所が変わる 1件」「変わらない 8件」「ファイルから消えた 1件」のように件数でまとめ、行ごとに「前 → 後」を出す。変わらない行は畳んでおく。

### 8.5 当日の急な変更

- 一番速いのは、ファイルの修正を待たずに **Studio のイベント編集画面で時刻を直して公開する**こと（今でもできる）。次にファイルを取り込んだとき、ファイルの値が同じなら差分は出ない。違えば §8.3 の確認が出る。
- 取り込み結果の画面に［変わった予定をアプリに反映する］ボタンを置き、変わったイベントを選んだ状態で今の公開確認を開く（第2段階）。
- 第4段階の候補：「この予定以降をまとめて10分遅らせる」。当日の遅れは後ろの予定にも波及することが多いため。
- アプリ側が新しい内容を受け取るまでの時間は Studio の外（iOS の取得の間隔）で決まる。当日の運用で重要なので、別途 NexusMobile 側で確認する。

## 9. 担当者名を残さない（プライバシーと安全）

**担当者名は取り込まない・保存しない・ログに出さない・公開しない。** これを設計で守る：

1. **入口で捨てる。** 読むのは「時間・所要時間・内容・特記」の4列だけ。サーバーが受け取る形（DTO）に、担当者のための項目を作らない。
   - 貼り付け（第1段階）：列の選択はブラウザの中で行い、**メイン担当の列と表の下の一覧は、サーバーへ送る前に捨てる**。名前はサーバーに届かない。
   - .xlsx（第2段階）：ファイル全体がサーバーに届くので、**メモリ上でだけ読み**、ディスク・DB・一時ファイルに置かない。読み終えたら4列だけの行を返し、元のファイルは保持しない。大きさの上限（例 2 MiB）を設ける。
2. **表の終わりで止める。** 最初の空行、または見出しに「担当」を含む行以降は読まない。表の外のセルも読まない。
3. **原文を保存しない。** 取り込みの記録（例：`studio.schedule_import_runs`）には、日時・実行した管理者・行数・分類ごとの件数・ファイルの SHA-256 だけを残す。セルの値は残さない。ファイル名を残すかはオーナーの判断（§13 の D5。ファイル名に名前が入る運用ならやめる）。
4. **ログに値を出さない。** 例外やエラーのメッセージにセルの値を入れない（「5行目の時刻が読めません」は良い、「5行目『…』」は出さない）。操作ログ（`operation_logs`）は今どおりイベントのタイトルを使う。
5. **残る危険：自由記述の欄。** 内容・特記の欄に名前が書かれていると（例「〇〇先生の模擬授業」）防げない。名前の一覧を Studio に持つと、それ自体が名前の保存になるので持たない。代わりに、確認画面で「参加者向け」の行のタイトルを必ず目で見てから確定する手順にする（件数を確定ボタンの横に出すのもそのため）。
6. **テスト。** ダミーの名前（例「試験 太郎」）を担当の列・表の下の一覧・表の外に入れた見本で取り込み、次を確かめる：
   - DB の `studio` schema の全テーブルの文字列を書き出し、ダミーの名前が1件も無い。
   - テスト中に記録された ILogger の出力と `operation_logs` にも無い。
   - 返した API の応答（確認画面のデータ）にも無い。
   - 貼り付けの場合は、送信前の行データ（ブラウザ側の変換関数）に無いことを単体テストで確かめる。

**外部のサービス（AI の文字読み取りなど）に PDF や画像を送る方式は採らない。** 名前が外に出るため。

## 10. 読み取りの方法

### 10.1 形式の比較

| 形式 | 結合セル | 色・赤字 | 時刻 | 安定性 | 判断 |
|---|---|---|---|---|---|
| Excel から貼り付け（TSV） | 結合セルの値は左上だけに入り、ほかは空になる | 失われる | 表示どおりの文字（"9:10"） | 高い。ブラウザだけで読める | **第1段階** |
| .xlsx ファイル | 範囲が分かる | 塗り色・文字色が読める（テーマ色は解釈が必要） | Excel の時刻値（1日の割合）か文字 | 高い | **第2段階** |
| PDF | 分からない | 一応読めるが不安定 | 文字 | 低い。版ごとに文字の位置・改行が変わり、表の列の推定が壊れやすい | **採らない** |

PDF しか届かない場合の運用は、「Excel の元ファイルを送ってもらう」とする。ファイル名の「(13)」から分かるとおり、元の Excel は作っている人の手元に必ずある。

参考：Excel から貼り付けると、ブラウザには TSV のほか HTML（結合や色を含む）も渡るため、将来は貼り付けでも色を読める。ただし Excel の版で中身が変わるため、第1段階では TSV だけを使う。

### 10.2 .NET のライブラリの候補（第2段階）

| ライブラリ | ライセンス | 結合セル | 色 | 所見 |
|---|---|---|---|---|
| **ClosedXML** | MIT | ○ | ○（テーマ色・濃淡も取れる） | 読みやすい API。依存は Open XML SDK。**推奨** |
| DocumentFormat.OpenXml（Open XML SDK） | MIT | ○ | ○（自分でスタイル表をたどる） | Microsoft 製の低レベル部品。手間は大きいが依存が最小 |
| NPOI | Apache-2.0 | ○ | ○ | 古い .xls も読める。API が Java 由来で冗長 |
| ExcelDataReader | MIT | ○ | × | 値の読み取りだけ。色が要らないなら軽い |
| Sylvan.Data.Excel | MIT | × | × | 速いが、今回の用途（結合・色）には足りない |
| EPPlus | 第5版以降は Polyform Noncommercial（商用は有償） | ○ | ○ | **ライセンスの点で採らない** |
| （PDF）PdfPig | Apache-2.0 | — | — | PDF を採るなら候補。今回は採らない |

ライセンスの種類は 2026-11 時点の認識。導入する PR で、その時の版とライセンスを NuGet で確かめて記録する（CLAUDE.md：新しいライブラリは理由と代替案を添える）。

### 10.3 読み取りの細かい点

- 時刻：`9:10`、`09:10`、全角、`9時10分`、`9:10~`、Excel の時刻値を受ける。`25:00` などは読めないとする。
- 所要時間：`30分`、`30`、`1時間`、`1時間30分`、`90分`。それ以外は空欄と同じ（確認画面で示す）。
- 結合セル：時間が結合されて内容が2行ある場合は「同じ時刻の2つの予定」。内容が「A / B」の1セルなら §4 のとおり選ぶ。
- 見出し行：「時間」「内容」などを含む行を見出しと見なし、列の位置を決める。見つからなければ、列の割り当てを画面で選んでもらう（貼り付けでも同じ）。
- シートが複数（AM版・PM版）：.xlsx ではシートを選ぶ。

## 11. 操作する人のための画面（提案）

対象は技術に詳しくない担当者1人。Figma に無い画面なので、**実装前に構成案の承認が要る**（CLAUDE.md）。

1. 「タイムスケジュールを取り込む」（Events の一覧から入る）
2. 開催回と日にちを選ぶ
3. 貼り付ける（第2段階はファイルを選ぶ）
4. 確認画面：行ごとに「時刻・予定名・場所・分類」と「前回からの変化」。足りないものは行の横に短く書く
5. ［参加者向け 9件を下書きにする］
6. 結果：「9件を下書きにしました。アプリに出す前に、場所が決まっていない予定が2件あります」と、次にすることへのボタン

言葉づかい：

- 使わない言葉：bundle、publish、Revision、canonical ID、TSV、パース。Studio の他の画面にある「公開」は、この画面では「アプリに反映（公開）」と添える。Spot は「場所」と書く。
- エラーの例：
  - 「5行目の時間『9;10』が時刻として読めません。『9:10』のように直して、もう一度貼り付けてください。」
  - 「『PC教室』がどの場所か分かりません。下の一覧から選んでください。選ばなくても下書きにはできます。」
  - 「時間・内容の見出しが見つかりません。表の見出しの行も含めてコピーしてください。」
  - 「この間に、別の人が同じ予定を直しました。最新の内容で確認し直します。」（今の保存競合の考え方と同じ）
- 確定の前に必ず確認画面を通す。確認画面では何も保存しない。

## 12. 選択肢の比較

| | A：貼り付け→下書き | B：.xlsx アップロード→下書き | C：PDF の読み取り |
|---|---|---|---|
| 先生方の作業 | 変わらない | 変わらない | 変わらない |
| 担当者の手間 | Excel を開いて表をコピー | ファイルを選ぶだけ | ファイルを選ぶだけ |
| 担当者名がサーバーに届くか | **届かない**（ブラウザで捨てる） | 届く（メモリ上で捨てる） | 届く |
| 色・結合セル | 失う（分類は規則と確認で補う） | 使える | 不安定 |
| 新しいライブラリ | 不要 | ClosedXML（MIT） | PdfPig 等 |
| 壊れやすさ | 低い | 低い | **高い** |
| 作る量 | 小さい | 中くらい（A の中心を再利用） | 大きく、直し続ける必要 |

### 推奨

**A と B は入口が違うだけで、中心（分類・場所の対応・差分・下書き保存）は同じ。** 中心はサーバー側に作り、A から始め、B を足す。C は採らない。

## 13. オーナーに決めてもらうこと

## 14. 段階と作業量（目安）

作業量は、エージェントが実装し、オーナーが確認する前提の「作業日」。検証記録（`docs/検証記録/`）と OpenAPI 更新を含む。

| 段階 | 内容 | 目安 | アプリに出るか |
|---|---|---|---|
| 0 | オーナーから資料（§15）と D1〜D6 の回答。画面の構成案の承認 | 0.5〜1日 | — |
| 1 | **貼り付け取り込み（新規のみ）**：列の割り当て・名前の列を捨てる・時刻の読み取り・分類の候補・場所の対応表（選んだら覚える）・予定名の対応表・確認画面・下書きの作成。名前が残らないことのテスト | 4〜6日 | 地図の公開後 |
| 2 | **取り込み直し**：取り込みのつながりの記録・差分の確認画面・上書きする項目の決まり・「消えた予定」・［変わった予定をアプリに反映する］ | 4〜6日 | 同上 |
| 3 | **.xlsx のファイル取り込み**：ClosedXML・結合セル・色を分類の候補に・シートの選択・大きさの上限。対応表の管理画面 | 3〜5日 | 同上 |
| 4 | 当日向け：「以降の予定をまとめて遅らせる」など | 2〜3日 | 同上 |

**最小の第一歩は段階1**：1つの開催回の1日分を、貼り付けで下書きにできるところまで。これだけで「先生方のファイルから Studio の下書きを作る」が成り立ち、2回目以降も（差分は無いが）作り直しで回せる。

## 15. オーナーに用意してもらうもの

**担当者名の入ったファイルは送らないでください。** 名前は「担当A」「担当B」のような置き換えにしてください（列ごと消すより、置き換えのほうが「名前の列を確かに捨てる」試験に使えます）。

1. 2026-11-14 の元の **.xlsx**（担当者名を置き換えたもの。表の下の担当者一覧も置き換え）。
2. **PM版**があれば、同じく置き換えたもの。1つのファイルに両方のシートがあるなら、そのまま。
3. 同じ開催回の**過去の版を2〜3個**（例：(11)(12)(13)。置き換えたもの）。差分の試験に使います。無ければ、(13) を元に「時間を1つずらした」「予定を1つ足した」版を作っていただいても構いません。
4. 行の**色の意味**と、時刻が**赤字の意味**。
5. 特記に出てくる場所の書き方と、実際の部屋（例：PC教室はどの部屋か、CTC2 は建物全体か特定の部屋か）。
6. ファイルがどう届くか（メールの添付、共有フォルダなど）と、当日の変更がどう伝わるか。
7. 毎回同じ形の表か（列の並び・見出しの書き方が変わるか）。
8. §13 の D1〜D6 の回答。

## 16. 危険と対策

| 危険 | 対策 |
|---|---|
| 内容・特記に名前が書かれる | 確認画面で参加者向けの行を必ず目で見る。名前の一覧は持たない（§9-5） |
| スタッフだけの行を誤って参加者向けにする | 分類の候補＋確認画面＋確定ボタンの横の件数。取り込みは下書きだけで、公開前にもう一度差分を見る |
| 表の形が回ごとに変わる | 見出し行で列を決める。見つからなければ列を選んでもらう |
| 同じ予定の判定を誤る（改名・同名が複数） | 自動で決めにくいものは候補として出し、オーナーが選ぶ。自動で消さない |
| Studio で直した内容を取り込みが消す | 上書きする項目を限る（§8.3）。食い違いは確認画面で選ぶ |
| 地図が無くてアプリに出せない | 取り込みとは別の課題（D4）。Validation 画面で足りないものを一覧できる |
| 当日の変更が間に合わない | Studio の編集画面で直接直す道を残す。アプリへの反映の間隔は NexusMobile 側で確認 |
| 新しいライブラリの脆弱性・ライセンス変更 | 第2段階で導入するときに版を固定し、ライセンスを記録。第1段階はライブラリ不要 |
