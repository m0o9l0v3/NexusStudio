## 1. 決定事項と本書の提案の境界

### 決定済み・利用者の明示条件

- 登録済み管理者は編集・検証・Preview・公開を1人で完結できる。別担当者による承認は必須にしない。
- 下書きと公開内容を分離する。イベントは1件単位、地図はひとまとまりで公開する。
- イベント内の項目単位の部分公開は含めない。選んだ変更を公開済みデータと組み合わせて検証する。
- 公開失敗時は直前の公開版を維持する。公開履歴と復旧をv1.0要件に含める。
- 建物・道路の新規作成はv1.0に含めない。
- 午前・午後の繰り返し、複数日の開催はよくある。複数教室の利用は将来発生し得る。
- 複数会場の入力UIを初回のv1.0実装範囲に含める。

### 本書で具体化する案

イベントの共通情報と開催枠を分け、開催枠に1つ以上のSpotを結び付ける。通常は会場欄を1つ表示し、「会場を追加」で増やす。状態、必須入力、画面文言、検証の強度、復旧手順などの新しい細部は提案として扱う。

## 2. 管理する情報の構造

| 単位 | 内容 | 関係 |
|---|---|---|
| イベント | ID、タイトル、説明、カテゴリ、画像、対象の開催 | 公開の単位。共通情報をまとめる |
| 開催枠 | 枠ID、日付、開始・終了時刻、通常／中止、中止案内 | 1イベントに複数登録できる |
| 開催枠の会場 | Spotのcanonical ID、会場補足、表示順 | 1開催枠に複数登録できる |
| 管理情報 | 作成者・更新者・保存日時・公開履歴・版情報 | システムが管理する |

- Event IDと開催枠IDは別の安定したIDとする。枠を複製したら新しいIDを発行し、日時変更だけなら枠IDを維持する案。
- Spotの参照はcanonical IDを保持する。`Spot.Code == SpotDto.Id == canonical ID`、大文字・小文字を保持するルールを引き継ぐ。
- 会場名の自由入力だけでSpotとの関連を代替しない。
- 元資料の単一の`Event.spotId`案は、「イベント → 開催枠 → 会場 → Spot」へ見直す。これは概念設計であり、APIフィールド名や移行方式の確定ではない。
- 下書きは開催枠0件・会場未選択でも保存できる案。公開には開催枠1件以上、各枠に会場1件以上を要求する。
- 日時入力はキャンパスの現地時刻として扱い、初期案は日本時間を明示する。保存形式は別途設計する。
- 1つの枠は原則として同一日の開始・終了で表す案。終日・日をまたぐ開催は未確定事項に残す。

### 登録例（架空の操作説明用。正式データではない）

```text
ロボット操作体験［タイトル・説明・カテゴリ・画像を共通管理］
  9月20日 10:00–11:00 → 101教室
  9月20日 14:00–15:00 → 101教室
  9月21日 10:00–11:00 → 101教室・102教室
```

同じ時間に実際に使う場所は同じ枠へ登録する。時間が異なる場合は別枠にする。候補地・未確定の場所は公開会場に混ぜない。「受付」「体験会場」のような補足は案内文であり、経路の経由順や必須立ち寄りを意味しない。

## 4. 画面と操作フロー

### 4.1 一覧

検索・絞り込み・新規作成を上部に配置し、主領域は表にする。複数会場をすべて表に詰めず「101教室、ほか1会場」等で要約する。イベントを選択すると編集画面へ進む。複数選択時に「選択したイベントを公開」を表示し、非公開対象や変更なしの対象をどう扱うか結果を明示する。

### 4.2 編集画面

中央に共通情報と開催枠、右側にPreview／検証結果を配置する案。上部にイベント名、公開状態、保存状態、「下書き保存」「公開内容を確認」を置く。取り下げ・履歴・変更破棄は区別した操作として配置する。

```text
イベント名　公開中・未公開変更あり　未保存
                              ［下書き保存］［公開内容を確認］
共通情報                                   Preview／検証結果
  タイトル・説明・カテゴリ・画像            開催枠を選んで確認
開催枠                                     会場一覧／中止案内
  9月21日 10:00–11:00 ［複製］
    会場1：101教室  建物・階・ID
      会場補足：受付                 ［解除］
    会場2：102教室  建物・階・ID
      会場補足：体験会場             ［解除］
    ［会場を追加］
  ［開催枠を追加］
```

この図は情報配置の案であり、Figma承認や最終レイアウトを意味しない。

### 4.3 会場を追加する

1. 「会場を追加」で検索欄を開く。
2. 名称・別名・canonical IDで検索する。必要に応じて建物・階で絞る。
3. 候補に名称・建物・階・ID・公開状態を表示し、同名の教室を区別する。
4. Spotを選ぶと行を追加し、地図で位置を確認できる。同じ枠で選択済みのSpotは再選択できない。
5. 必要なら会場補足を入力し、上下移動ボタンで表示順を変える。ドラッグ操作だけを必須にしない。
6. 解除はこの開催枠との関連だけを外し、Spotや他の枠の会場を削除しない。

会場0件でも下書き保存は可能とし、「公開には会場が必要です」と表示する案。未公開Spotを選択可能にする場合は行に未公開と明示し、公開時に阻止する。公開済みSpotに未公開の地図変更がある場合は、イベント公開で利用される公開済み属性を基本に表示する案。

### 4.4 繰り返し・複数日を登録する

最初の枠を作成 → 複製 → 午後へ時刻変更 → 必要に応じ複製して翌日へ日付変更 → Previewで各枠を確認 → 下書き保存、と進める。複製後は新しい枠にフォーカスし、複製直後の重複が分かるようにする。

### 4.5 公開する

未保存なら保存を案内 → 保存版を検証 → 共通情報・枠の追加／日時／会場／中止／削除の差分を表示 → 公開対象と警告を確認 → 公開実行 → 結果・公開版・日時を表示する。

Previewには「編集中の内容」「公開中の内容」を明示する。未保存の内容をPreviewできても、そのまま公開できたと誤認させない。

## 5. 状態と急ぎの変更

| 状態 | 管理上の意味 | アプリへ提供する内容 |
|---|---|---|
| 未公開 | 公開履歴のない下書き | 公開しない |
| 公開中 | 公開版と保存済み下書きが一致 | 公開版 |
| 公開中・未公開変更あり | 公開版とは別に変更を保存 | 公開版を維持 |
| 取り下げ済み | 公開を終了、管理データと履歴は保持 | 通常の一覧・検索から除外する案 |

未保存・保存中・保存失敗は上表と別に表示する。開催状況も別で、枠ごとに通常／中止を保持する。イベントの「一部中止」「全枠中止」は枠から集約し、独立した矛盾する状態を手入力させない案。

### 急ぎの訂正で可能なことと限界

- 別イベントや地図の未完成下書きに影響されず、対象イベントを公開できる。
- 同じイベント内の開催枠と共通情報の変更はすべて公開対象になる。枠だけの部分公開はしない。
- 午後枠だけを中止にしても、そのイベント内に別の編集があれば一緒に公開されることを差分画面で明示する。
- 同じイベント内に公開できない変更が残る場合は、内容を修正して整える必要がある。この制約は1件単位公開の境界として残る。
- イベント全体の取り下げは、編集中の内容を公開せず実行できる専用操作とする案。

## 6. 検証ルール案

下書きの入力不足は保存を妨げない。一方、壊れた参照形式や不正なファイルなど、システムで扱えない入力は保存段階でも受け付けない。検証結果にはイベント・開催枠・会場行への修正導線を持たせる。

| ID | 判定 | 条件／動作 |
|---|---|---|
| E01 | 公開阻止 | 必須の共通情報が不足している。必須項目は最終決定に合わせる |
| E02 | 公開阻止 | 開催枠0件、日付・時刻不足、終了が開始以前 |
| E03 | 公開阻止 | 開催枠に会場がない。同じ枠に同じcanonical IDが重複 |
| E04 | 公開阻止 | 参照Spotが存在しない、未公開、または会場として利用できない公開状態 |
| E05 | 公開阻止 | 設定した画像が処理中・失敗・参照不能。画像の解除か修正を案内 |
| E06 | 再確認 | 確認後にイベント、公開の基準版、関連するSpot等が変更された |
| W01 | 確認を促す | 開催日時が選択したOpen Campusの期間外 |
| W02 | 確認を促す | 日時・会場集合が完全に同じ枠が存在する |
| W03 | 確認を促す | 過去の枠を追加・日時変更して公開する。無変更の過去枠で毎回警告しない |
| W04 | 確認を促す | 中止へ変更する際に案内文がない |

時間帯の重なりだけではエラーにしない。複数会場での並行開催があり得るため。会場の予約・占有・定員管理は本案の検証範囲に含めない。

中止枠も日時と会場の情報を保持する基本案。過去・中止枠が参照するSpotを後から取り下げる場合の履歴保持・表示方針は、地図公開との契約で確定する。参照切れを無条件に許す実装にはしない。

## 7. 保存・公開・履歴・復旧の要件

- 同じイベントを別タブや別管理者が変更した際、古い内容で無断上書きしない。競合時は入力を失わせず、最新状態の確認を案内する。
- 公開対象は確認した保存版へ固定する。関連状態が変わった場合は再検証し、確認が必要な差分を示す。
- 一括公開は選択した全対象で成立する場合のみ反映する。エラーのある対象を管理者が選択解除し、残りを再確認して公開できる。
- 公開の連打・通信の再試行で重複した公開を作らない。結果が不明な場合は状態確認を行い、成功・失敗を推測表示しない。
- 公開済みのイベントと参照先地図を、整合する組み合わせで利用できるようにする。サーバーでの一括反映だけで端末上の整合性を保証したと扱わない。
- 履歴には操作種別・対象・実行者・日時・対象版・差分・結果を記録する。公開メッセージは任意とする案。
- 復旧は過去のイベント全体を候補とし、現在の関連データと再検証して新しい公開を作る案。地図や別イベントを同時に過去へ戻さない。
- 復旧時に既存の未公開変更がある場合は、消失しないよう退避し、扱いを明示する案。退避内容の表示・復元操作と保存期間は要設計。

## 8. iOS・配信側との連携要件

複数会場を保存できることと、利用者が正しい会場へ案内されることをセットで完成条件にする。以下は必要な連携要件であり、現行iOSの実装済み機能とは断定しない。

- イベント詳細で複数日・複数枠を表示し、選択した枠の会場一覧と中止案内を表示する。
- 複数会場なら目的地を選んで経路案内を開始する。先頭の会場へ暗黙に案内しない。
- 経路案内には選択したSpotのcanonical IDを渡す。架空の代表地点や会場座標の平均で代用しない。
- 中止枠は開催中と誤認させない。過去枠・全枠中止イベントの一覧での見せ方は別途決める。
- 取り下げ後にお気に入り・直接リンクから開かれた場合は、公開終了が分かる表示を検討する。通常一覧からの除外と分けて設計する。
- 保存形式・API・既存の単一会場データの移行・旧クライアントとの互換性を確認する。複数会場を旧形式の1会場へ黙って切り詰めない。
- 必要なAPI・アプリ対応の前に、対応不能な複数枠／複数会場データを本番公開しない。開発時は下書き・Previewとして扱える。
- 公開後の更新取得タイミング・キャッシュ・オフライン時の表示を別途定義する。Studioの公開完了は全端末での即時表示完了を意味しない。

|---|---|---|
| AC01 | 単日・1枠・1会場を登録 | 会場追加操作なしで登録・Preview・公開まで進める |
| AC02 | 午前枠を複製して午後へ変更 | 共通情報の再入力なしで2枠を作れ、枠IDは別になる |
| AC03 | 枠を複製して翌日へ変更 | 1イベントに複数日の枠を保持し、日付順に確認できる |
| AC04 | 1枠へ2会場を登録 | 両方の名称・建物・階・補足を保存し、Previewに表示する |
| AC05 | 同名の教室を検索 | 建物・階・IDで区別して選択できる |
| AC06 | 同じ枠へ同じSpotを再追加 | UIで防ぎ、保存・公開側でも重複を検出する |
| AC07 | 片方の会場を解除 | その枠の関連のみ解除し、Spotや他の枠に影響しない |
| AC08 | 会場をすべて解除して保存 | 下書き保存できるが公開は阻止し、修正先を示す |
| AC09 | 未公開Spotを会場に指定 | 公開阻止の理由を示し、Spotを自動公開しない |
| AC10 | 地図に無関係な下書きエラーがある | 公開済み会場を使うイベントの訂正は公開できる |
| AC11 | 午後枠だけ中止にして公開 | 午前枠は通常、午後枠は中止として提供される |
| AC12 | 同じイベントに他の変更もある | 中止操作の公開確認で他の変更も明示される |
| AC13 | 不完全な下書きのある公開イベントを取り下げ | 下書きを保持し、その内容を公開せず取り下げられる |
| AC14 | 一括公開対象の1件にエラー | 全対象を未反映に保ち、選択解除後に残りを公開できる |
| AC15 | 確認後に関連Spotの公開状態が変わる | 古い確認結果で公開せず、再検証・再確認する |
| AC16 | 公開処理が失敗・通信結果不明 | 一部反映や重複公開を防ぎ、実際の状態を確認できる |
| AC17 | 過去版へ復旧する | 現行の参照先で検証し、新しい公開履歴として残る |
| AC18 | 複数会場の枠からアプリで案内開始 | 選んだSpotへ案内し、先頭会場を暗黙選択しない |
| AC19 | マウスを使わず会場を追加・並べ替え | 検索・選択・解除・順序変更をキーボードで操作できる |
| AC20 | 保存競合が起きる | 無断上書きせず、入力と最新状態を確認できる |

## 10. v1.0に含めない案・未確定事項

### 対象外とする案

- 定期開催ルールによる自動生成（毎週・隔週等）。初期は枠の複製で対応。
- 開催枠単位・項目単位の部分公開。公開単位はイベント1件のまま。
- 枠ごとの独立したタイトル・説明・画像。初期は共通情報を使用。
- 会場予約、定員、参加申込、チケット、待ち列、リアルタイム混雑。
- 複数会場を順番に巡る専用経路の編集。
- 高度な文章装飾、独立したメディアライブラリ、CSV一括登録。

### 次に決める事項（初期案を併記）

| 項目 | 初期案／確認点 |
|---|---|
| 対象の開催 | 開催回に複数の開催日を持たせ、イベントを1開催回へ関連付ける案。実際の開催管理単位を確認する |
| 終日開催 | 時刻必須を基本案とし、終日や開催時間内随時の企画があるか確認する |
| 日またぎ | 同日内を基本案とし、必要性があれば入力・検証を拡張する |
| カテゴリ | 1つ選択を基本案とし、正式候補・複数選択の必要性を確認する |
| 説明 | 公開時必須案。正式な入力方針に合わせて決める |
| 中止案内 | 入力を促す警告案。必須にするかを決める |
| 過去・中止枠の会場 | Spotの取り下げ時に残す履歴情報と、公開中の案内・経路ボタンの扱いを決める |
| 復旧と既存下書き | 退避・復元UI、保持期間を決める。詳細未設計のまま完成扱いにしない |
| 数量・容量の上限 | イベント・枠・会場・文字数・画像の実用上の上限を決める |
| 配信互換性 | 既存API・iOS・オフラインデータの調査後、変更範囲と提供順を決める |

## 11. 実装へ分ける際の順序案

1. 既存API・イベントデータ・iOS表示を読み取り調査し、開催枠・複数会場の契約と移行案を定める。
2. 共通情報・開催枠・会場検索／追加／解除／順序変更・下書き保存を実装する。
3. Preview・差分・検証・イベント単位公開と一括公開を実装する。
4. 中止・取り下げ・履歴・復旧・競合対応を実装する。
5. アプリと配信の対応を整え、受け入れ条件を通して本番利用可能と判断する。

本書作成では、コード・API・Figma・iOS・外部Issue・本番データを変更していない。元の公開方針記録も変更していない。
