## 1. 結論

**隔離した開発環境で、イベントの複数枠・複数会場を下書き保存して再表示する実装は開始できる。本番公開の開始条件は満たしていない。**

1. 再利用の中心はReact／TypeScriptの開発資産、ASP.NET Core／EF Core／PostgreSQLのAPI・DB基盤、canonical ID・座標契約、地図変換CLI、SwiftUIの画面・取得境界・遷移テストである。
2. 現行のEvent／Spot更新は公開用の行を直接書き換える。下書きと公開版の併存、Release、確認した版への固定、選択公開、一括反映、復旧は新設が必要。
3. Eventには単一日時と自由入力の場所しかなく、Spotへの確定参照もない。既存OpenCampusTimeslotはQR／Exhibit系のモデルであり、Studioの開催回・開催日・イベント枠としてそのまま転用できない。
4. SwiftUI版の本番既定はデータ取得・地図・経路が未接続。保存版の表示状態はあるが、ダウンロード・永続保存・整合する版の切り替えを実装済みとはいえない。
5. 原本GeoJSONは26地物、25 Polygon＋1 LineString。metadataはdraft_only。現行の公開Schemaには建物高さ・階数・MultiPolygonがなく、原本をそのまま公開することも、公開用変換結果を編集原本に戻すことも不適切。
6. 推奨はReact＋ViteのPC Web、既存.NET API基盤の拡張、PostgreSQL、個別管理者のIdentity＋同一オリジンCookie、MapLibre GL JS＋Mapbox GL Draw。保存は編集Revisionと不変の公開Releaseを分離する。選定の成立条件は15に記載する。

### 3.1 管理認証

`AuthController.Login`は設定にある単一Username／Passwordとの完全一致でJWTを発行する。`AdminAccess`は認証済みでOwner／Moderator／Devのroleを要求し、Event／Spot／OcDayのControllerを保護する。JWTにはsub／jti／roleが入り、失効確認のフックもある（N06、N14）。

ただし管理者ユーザーテーブル、個別管理者の登録・無効化・復旧、MFA、現在のUIのログイン導線は確認できない。既存WebクライアントはlocalStorageのadminTokenを読む。**全管理者が同じ権限を持つ要件と、全員が同じアカウントを共有する実装は別である。** ユーザー管理の基盤は新設し、管理APIの認可境界を維持する。

### 3.2 起動による副作用

Admin APIのProgramは起動時にDbSeeder.SeedAsyncを呼ぶ。SeederはSQLiteならEnsureDeleted／EnsureCreated、その他ならMigrateを実行し、開発用Spot等を追加する（N07）。環境限定の安全な起動になっていないため、本調査ではアプリを起動していない。今後の初期実装では既存DBを使わず、明示的に作成した使い捨てPostgreSQLで確認する。

### 3.3 テストの実質

APIのxUnit、SwiftUIのXCTest、旧ExpoのJest、MapDatasetのNodeテストが存在する。監査テストの一部はEF InMemoryであり、実PostgreSQLのトランザクション／競合保証の証拠にはならない。ナビテストには大文字小文字を無視する旧動作を期待するものがある。SwiftUIのClientBoundaryTestsは未接続がfixtureへすり替わらないことを確認するテストであり、実通信成功のテストではない（N15、I04）。今回、既存のテストスイート全体は実行していない。

### 4.1 既存の会場推測は採用しない

Public EventsController.ResolveSpotCodeはlocationTextをOrdinalIgnoreCaseで公開Spot.Codeへ照合し、見つからなければ座標から30m以内の最寄りSpotを返す（N11）。これは新しい契約の完全一致・未知地点の非代替方針と一致しない。同じ建物の別階・近接教室を誤って選ぶ可能性があるため、**表示名や近傍推測の結果を正式な会場移行表にしてはならない**。

### 5.3 座標・階・高さの契約

- E1-5の採用済み契約：公開geometryはWGS84／OGC CRS84、2D `[longitude, latitude]`。`crs`と第3座標なし。出力小数6桁。高さをgeometryの第3成分へ入れない（G02）。
- 屋内入力はfloor-localのm、右向きx／上向きy。SVGに描画するときだけY反転。ENUを介した2D相似変換。fit 3点以上＋独立check 1点以上が必要。今回のGPS記録に対応するfloor-local座標・承認済みアンカー一式はない。
- 階IDは例`mb_2f`。教室IDの一部`f2`から機械的に階IDを切り出さず、明示的なbuildingId／floorId参照を持つ（G01）。
- 建物高さ、教室高さ、階数、階の識別子、基準標高、Graphの階層接続は別データ。どれか一つから他を生成して正式値にしない。
- 古いPDFは今回の値の根拠に使用していない。

| 検証 | DataAnnotations、Spot.Code重複等。Event終了＞開始、正式会場、複数枠は未対応 | 保存の構造検証と公開の完全性検証を分離 |
| 競合 | row version／ETag／If-Matchは対象更新処理にない | Revision比較、409／412、入力保持 |
| 一括反映 | 単一SaveChangesはあるが、複数HTTP操作の一括公開はない | DB transaction内でRelease記録・pointer・操作結果をcommit |
| 重複防止 | 公開操作ID・Idempotency-Keyなし | キーとrequest hashの一意性、同じ結果の再取得 |
| 履歴・復旧 | 公開snapshotなし。Deleteは物理削除 | 不変Revision、取り下げ記録、現在の参照を使う復旧候補 |
| 画像・地図保持 | 旧素材の保持・削除判定なし | Release／下書き／復旧候補からの参照を考慮した保持 |
| 災害復旧 | 対象の運用資料にバックアップ・復元試験の証拠なし | DB＋素材＋鍵を含む復元手順と別環境での演習 |

EF Coreの通常のSaveChangesのトランザクション保証を、アプリ全体の選択公開保証へ拡大解釈しない。競合トークン・明示トランザクションは基盤として使える（公式O07、O08）。

### 6.2 推奨する振る舞い

公開候補＝現在の公開Releaseの参照集合＋選択した保存Revision。選択外の下書きは読み込まない。公開候補を検証し、承認画面に表示した候補hash・基準Release・選択Revisionが同じ場合だけ確定する。実装詳細は15。

| 変更 | 推奨する処理 |
|---|---|
| 開催日の一般公開時間変更 | 公開中イベントRevisionのallDay指定から時刻を再解決。開催情報と派生配信内容を一つのReleaseにする。編集中の説明・会場は混ぜない |
| 開催日中止／再開 | 実効中止＝公開開催日の中止 OR 枠独自中止。両方の理由を保持。親を再開しても枠独自中止は残す |
| Spot／カテゴリ新規選択停止 | 現在公開している同一参照の維持を許可。下書きのみの参照・新しい枠への割当は新規として検証。別Spotへ自動置換しない |
| Spot取り下げ | 公開中イベント・Graphの参照が残れば地図公開を止める。過去／中止枠を含む既存公開参照も初期は保護する保守的案 |
| カテゴリ取り下げ／削除 | 初期は新規選択停止で運用。公開参照中の物理削除は行わない。カテゴリ一覧の復旧で参照を失う場合は阻止 |
| イベント取り下げ | 公開の参照から除外し、tombstoneを記録。未完成下書きを保持し、その不足で取り下げを止めない |
| イベント復旧 | 過去のイベント全体＋現在の公開地図／カテゴリ／開催情報を検証し、新Release。終日時刻は現在の参照から再解決 |
| 地図復旧 | 過去の地図一式を候補にする。現在公開のEventが参照するSpot等を失えば阻止。無関係なイベント下書きは保つ |
| 下書き保護 | 復旧をDraft headへ上書きする必要はない。Revisionを不変保存し、Draft headをそのまま保持する簡素化を推奨。basePublishedRevisionとの差を表示 |

終日時刻の再解決は通常のイベント項目部分公開とは別の派生配信処理として明示する。これは08／11の追加案を簡素化した提案で、既存決定案を変更していない。

### 7.2 複数会場から案内までの変更箇所

1. `HomeModels.HomeEvent`をイベント・枠・会場のIDを区別できる表示モデルへ拡張する。共通タイトルに対して、今日の枠を複数表示できるadapterを作る。
2. `AppRouteRequest.eventDetails(eventID, canonicalSpotID)`は入口で既に1会場を要求する。複数会場ではeventId／slotIdから詳細へ入り、会場を明示選択する経路を追加する。
3. `AppRouteCoordinator`のeventDetails→MapStore.selectを拡張。選択完了後だけ`MapSelection.canonicalSpotID`を設定する。先頭会場や座標平均で代替しない。
4. `.route(destinationSpotID:)`とCanonicalSpotID型は維持できる。routeHandlerを同じMapDataset版に対応する端末内探索へ接続する。
5. 新しいPublishedContentClient／ReleaseStore（名称案）をHome／Search／Map／Guidanceの共通取得・保存元とする。必要な地図・Spot・Graph・基本案内を整合した版でオフライン利用する。

### 7.3 推奨配信境界

Public API v2でcurrent manifestを取得し、不変releaseIdに紐づくコンテンツと地図を取得する。端末は一時領域へ保存し、schema・hash・ID参照を検証してからactive releaseを切り替える。途中失敗・容量不足・再起動でも旧版を維持する。起動・foreground・手動更新を更新機会とする案で、更新頻度は実測後に調整する。

旧API v1は当面独立して維持するが、複数枠／会場や中止を1件へ黙って切り詰めない。配布済み端末の有無・更新経路を確認するまで、新契約の本番公開は停止する。旧版にできない表現を公開するには、対応iOSの配布と最低対応版の運用が先に必要。公開済み版を凍結しただけでは訂正・中止を伝えられないため、恒久的互換策にはしない。

Studioの公開成功はサーバーで整合した版が確定・取得可能になったことを表す。オフライン端末を含む全端末への即時反映は保証しない。期限切れ時は古いイベントを「今日開催」と表示せず、保存日時と未更新状態を示す。

## 8. E：地図技術の評価

### 8.1 推奨と比較

**MapLibre GL JS＋Mapbox GL Drawを推奨候補に固定し、代表データの編集往復試験を実装着手時の技術ゲートにする。** 2Dの頂点編集と3Dの高さ確認を分け、編集の正本はライブラリの内部storeとは別に保持する。

| 項目 | 推奨候補の根拠・制約 | 判定 |
|---|---|---|
| 2D・3D押し出し | MapLibreのfill-extrusionと高さ・baseの公式仕様／例 | 公式対応。実原本での描画性能は未測定 |
| 既存頂点の移動・追加・削除 | Drawのdirect_select、座標モデル、頂点操作 | 機能の存在を確認。PC UI統合試験は未実施 |
| 穴 | Draw Polygonモデルは複数ringを保持・再閉合 | 静的に確認。3頂点未満でringが消える処理があるため、穴の無断削除を防ぐアプリ側制約が必要 |
| MultiPolygon | Draw add APIで対応し、MultiFeatureモデルが各Polygonを保持 | 編集ライブラリの対応とNexus公開Schemaの対応は別。初期は保存保持・読取表示、公開はSchema改訂まで不可 |
| 未対応属性・外部メンバー | Draw.toGeoJSONはFeatureの決まった構造を再構成する | FeatureCollection.metadata、bbox等までの完全保持を保証しない。全原本をDraw.getAllで上書きしない |
| Spot編集 | Point読込・移動は対応範囲 | 座標編集結果を下書きへ適用。正式ID・出典・到着点は別に検証 |
| Undo／Redo | Draw APIに汎用の編集履歴契約はない | アプリで建物属性・geometry・Spotをまとめたcommand履歴を持つ。公開復旧とは別 |
| 道路・入口・Graph | MapLibreで別source／layerとして表示できる設計 | Drawへ編集対象として渡さず、未編集内容のhash／構造比較を保存条件にする |
| 自己交差・穴の包含 | Draw.isValidは頂点数中心 | サーバー側のtopology検証が必要。NetTopologySuiteのIsValidOpを追加候補とする |
| MapLibreとの接続 | MapLibre公式にDraw連携例あり | クラス名・style調整が必要。最新版同士を無試験で対応済みにしない |

有力な代替はTerra Draw。MITでMapLibre adapterがあり、描画ライブラリを交換しやすい。ただし確認した公式Store契約はPoint／LineString／Polygonのみで、Multi系非対応と明記。穴に関する拒否理由も存在するため、既存形状の保持要件に対して無条件採用しない。今回、最新Terra Drawの全mode・穴編集・Undo/Redoの実動作までは検証していない。MultiPolygonを勝手に別IDへ分割する回避策は採用しない。

一時ディレクトリ内の調査スクリプトから既存CLI／validatorを読み取り使用し、出力先を一時領域へ固定した。依存物の新規導入、DB、アプリ起動は不要だった。これは製品のブラウザ試験ではない。
