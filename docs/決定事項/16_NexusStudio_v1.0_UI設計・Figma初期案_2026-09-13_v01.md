## 2. 引き継いだ確定事項

- PCブラウザ専用。ログイン後はOverviewへ直接入る。
- 左Sidebar、中央Workspace、必要時の右Inspectorを基本とする。
- 登録済み管理者は編集・検証・公開・取り下げ・復旧を一人で完結できる。別管理者の承認を必須にしない。
- 下書き保存は公開内容を変更しない。
- イベントは1件全体、地図はひとまとまりで公開する。イベント内の項目・開催枠だけの部分公開はしない。
- 公開済みデータと選択した変更だけを組み合わせて検証し、無関係な下書きの問題で別イベントの訂正を止めない。
- イベントは「イベント → 開催枠 → 複数会場 → Spot」。Spot参照はcanonical IDを大文字小文字を保持して使う。
- 終日と時間内随時参加は別設定。終日は開催日の一般公開時間と具体的な開始・終了を示し、参照元が未登録・未公開なら未解決とする。
- 入力不足でも下書き保存できることと、公開可能であることを分ける。
- 建物・道路の新規作成はv1.0に含めない。

## 4. 状態一覧

状態は一つの巨大な列挙へまとめず、判断する場面ごとに分ける。

| 軸 | 状態 |
|---|---|
| 取得 | 読み込み中、正式0件、検索結果0件、取得失敗 |
| 編集保存 | 未保存、保存中、保存済み、保存失敗 |
| 公開 | 未公開、公開中、未公開変更あり、取り下げ済み |
| 検証 | 未検証、検証中、警告、公開阻止、検証処理失敗 |
| 公開処理 | 公開処理中、公開成功、未反映の失敗、結果確認中 |
| セッション | 認証期限切れ、同時編集競合、未保存離脱 |
| 画像 | 画像なし、アップロード中、画像処理失敗 |
| 正式情報 | 高さ・座標・出典・経路接続の未確認 |
| 開催 | 通常、開催日由来の中止、枠独自の中止、実効的な一部／全枠中止 |

今回Figmaで作成した代表状態は、未保存、保存済み、会場未選択による公開阻止、保存失敗、未保存離脱である。

## 5. UI基準の提案

以下はEventsで評価する推奨案であり、確定値ではない。

- 画面：1920×1080を広幅比較、1440×1024を最小側の作業確認に使用。
- 構造：Sidebar 216〜224px、Toolbar 64px、右Preview 400px。中央Workspaceを残りの幅へ伸ばす。
- 文字：Noto Sans JP。本文14px、補足11〜12px、見出し18px、画面タイトル22〜24px。
- 余白：4px基準。主要間隔8／12／16／24／32px。
- 角丸：入力・小操作6〜8px、カード10px。ピル型は状態ラベルに限定。
- 配色：薄灰Canvas、白Surface、濃紺本文、青を選択・主要操作に使用。黄は要確認、赤は公開阻止・危険操作、緑は成功に限定。
- 状態は色だけでなく、必ず日本語ラベルまたは説明文を併記する。
- 巨大KPIカードや装飾グラフは使わず、表・フォーム・地図を主役にする。

ライトテーマを初期案とした。ダークテーマは未確定で、今回の画面を確定した後に必要性を判断する。

## 6. Events配置案

- 上部Toolbar：現在の対象、サンプル表示、公開状態、保存状態、下書き保存、公開確認。
- 中央上部：イベント共通情報（タイトル、開催回、カテゴリ、説明。画像は次回のEvents詳細で追加）。
- 中央下部：開催枠を日付・開始時刻順に並べ、枠ごとに時間方式、参加方式、全会場、補足、canonical IDを表示。
- 右Inspector：`Device Frame → Screen → Preview Content`。Generic iPhone Frame内に固定論理Viewportを縮小表示する。
- Previewには「編集中／保存済み下書き／公開中／公開確認対象」と「近似表示」を明記する。
- 複数会場は先頭だけに省略せず、枠内とPreviewの双方で全件を確認できるようにする。

設計用サンプルとして「ロボット操作体験」、2026年9月20日・21日、`mb_f2_cr_2a`、`mb_f2_cr_2b`を使用している。正式イベント・正式日時・正式公開データではない。

## 7. 最初の主要操作フロー

FigmaのPrototype開始点：`11:2 E01 Events — 一覧`（フロー名「Events主要フロー」）。

1. `11:2` Events一覧で設計用サンプルの行を選ぶ。
2. `10:2` 午前枠を編集し、「午前枠を午後・別日へ複製」を選ぶ。
3. `10:130` 午後・別日の3枠を確認し、「午後枠へ二会場を設定し終日を確認」を選ぶ。
4. `2:2` 二会場、時間内随時参加、翌日の終日と参照時間を確認する。
5. `2:2` の「下書き保存」から `10:258` 保存済み状態へ進む。
6. `10:258` の「一覧へ戻る」から `11:178` 保存後一覧へ戻る。
7. `11:178` の対象行を開き、`10:386` で保存内容を再確認する。

代表状態：

- `12:2` 会場未選択。下書き保存は可能だが公開阻止。
- `12:102` 保存失敗。入力保持と再試行を明示。
- `12:232` 未保存離脱。編集へ戻る／変更を破棄／保存して戻るを選択。

## 8. Figma構造と確認結果

- 元の空フレーム`2:2`をEvents基準画面として使用し、元から存在しない製品画面を承認済み資産として扱っていない。
- Local Variables：Canvas、Surface、Text、Border、Brand、Success、Warning、Danger、Spacing、Radiusを作成。
- Local Text Styles：Title、Heading、Body、Body Strong、Captionを作成。
- Components／Variants：ButtonとStatus Badgeの基礎Variantsを作成。画面はAuto Layout中心で構成。
- 1440版`2:2`と1920比較版`14:2`をスクリーンショットで確認。文字切れ・主要要素の重なりは見つからなかった。
- `11:2 → 10:2 → 10:130 → 2:2 → 10:258 → 11:178 → 10:386`の遷移先IDを確認。
- 主なクリック領域は一覧行1176×72、枠784×148、明示アクション168×34／216×34、Toolbarボタン93×39。小さなアイコンだけに主要操作を依存させていない。

Figma内の保存・公開はPrototype上の表現であり、実DB保存・実公開・iOS実行ではない。

## 10. 次の確認単位と受け入れ観点

次は今回のEvents基準を利用者が確認・修正した後、差分・検証 → イベント1件の公開 → 公開結果を設計する。

- イベント全体の公開対象と、選択外の下書きが明確。
- 無関係な地図下書きのエラーが公開阻止に混入しない。
- 未公開Spot等の関連下書きを勝手に公開対象へ追加しない。
- 終日、随時参加、開催日由来の中止、枠独自中止を差分で区別する。
- 公開成功、未反映の失敗、結果確認中を推測せず表示する。
- Studio側の公開成功と、全iOS端末への反映完了を同じ状態として表示しない。

## 11. 実装時に別途検証する事項

- 1440程度の対象ブラウザでのキーボード操作、フォーカス順、拡大表示、長文、実データ量。
- API／DBを通した保存・再読込、競合、通信切断、重複防止。Figma Prototypeは証拠にしない。
- iOS実機での文章量、Safe Area、Dynamic Type、画像、全会場、中止・終日・随時参加表示。
- 正式なSpot台帳、開催情報、カテゴリ、座標・高さ・出典・経路接続。サンプル値から推定しない。
- Map Editorの頂点編集、3D性能、穴・MultiPolygon保持、Undo／Redoは実装時の技術ゲートで確認する。

本書とFigmaはUI検討の開始点。利用者が確認した対象だけを確定し、Eventsの確認をStudio全画面・本実装の承認へ拡張しない。
