**現時点でFigma上に完成している画面・表現は、原則としてUIの正とします。** そのデザインを活かして実装することが目的です。未完成部分や、運用・実装に必要な追加があれば遠慮なく提案してください。ただし、あなたの好みで完成済み画面を再設計したり、提案を承認済みとして扱ったりしないでください。

今回の依頼は「理解・不足分析・提案・実装準備」までです。調査を完了して具体案を提示してください。製品コードの実装とFigmaの変更は、結果を踏まえた次の実装・デザイン変更指示で開始します。

「Figmaに描かれていること」「資料で決まっていること」「あなたが補完を提案すること」を、常に区別してください。

## 3. 今回の進め方

### A. Figmaへのアクセスを確認する

利用できるFigma MCP・連携・ブラウザ等を確認し、実ファイルから構造と画面を取得してください。アクセスできる前提で架空のノード一覧や見た目を作らないでください。

Figmaへアクセスできない場合は、その事実と必要なURL・権限・共有方法等を簡潔に示してください。先に読めるローカル資料を確認し、未閲覧の画面を確認済みと報告しないでください。画像しか取得できなければ、構造・Variables・プロトタイプを確認できていないことを明記してください。

### B. 全体と代表画面を理解する

最初にページ・Section・トップレベルFrame・主要Componentを一覧化し、対象を絞って詳細取得してください。大きなファイルを一度に読み込み、出力が切れた状態で全画面確認済みとしないでください。

各領域を、実際の構造情報とスクリーンショットの両方で確認してください。主な対象はLogin、Overview、Events、Spots、Open Campus、Map Data、Validation、Releases、Logs、Preview、カテゴリ管理、共通ダイアログです。存在しない画面は未作成として記録してください。

画面ごとに、Figmaリンク・Node ID・目的・入力・主要操作・遷移先・関連状態・参照Component・確認した範囲をまとめてください。画面サイズ、長文や一覧のスクロール、Inspectorの高さ、選択・フォーカス、固定領域も確認してください。

### C. 操作を追う

プロトタイプの開始点・反応・クリック領域・遷移先を確認し、可能なら主要フローを実際に操作してください。静的確認と手動操作の結果は分けて記録してください。

1. Events一覧 → 1件編集 → 開催枠複製 → 複数会場設定 → 終日／随時参加の確認 → 下書き保存 → 一覧 → 再表示。
2. 未公開変更 → 差分・検証確認 → 公開処理中 → 成功／結果確認中／未反映の失敗。
3. Overview → 未公開変更や問題箇所 → 編集・検証画面 → 戻る。
4. Spots一覧 → 地図・Inspector選択 → 位置変更 → 確定／取消 → 下書き保存。
5. 未保存離脱、保存失敗、参照先不足などの途中分岐。

画面が存在するだけでフロー完了とは判定しないでください。未接続のボタン・到達できない状態・戻れない画面を、意図した未実装か不具合かも含めて整理してください。Figma上の保存成功は、実DBへの保存成功を意味しません。

### D. 仕様との差を調べる

「仕様項目 → Figmaノード／状態 → 実装に必要な情報」の対応表を作成してください。14・15の既存調査を活用し、UI実装に関係する部分だけ現コードで再確認してください。全技術調査を無目的にやり直す必要はありません。

最低限、次を確認してください。

- 複数日・複数枠・複数会場、終日と具体的時刻、随時参加、枠中止と開催日中止。
- 未保存／保存済み下書き／公開中／未公開変更あり／取り下げの区別。
- 読み込み中、正式0件、検索0件、取得失敗、保存情報、長い名称、多数の行・会場。
- 入力検証、保存失敗、同時編集、認証切れ、未保存離脱、公開結果不明、再試行。
- 会場・カテゴリの新規選択停止と既存参照、選択対象だけの公開と関連整合性。
- ID・位置・出典・経路接続の未確認表示、2D／3D・レイヤー・形状編集・Undo／Redoの境界。
- キーボード操作、フォーカス、色だけに依存しない状態表示、スクロール・ダイアログの操作。

状態が別Frameとして描かれていないだけで、必ず独立画面を追加すべきとは判断しないでください。Variant、共通ルール、実装時の状態定義で足りるものを分けてください。

### E. 不足・改善・追加案を出す

各提案に次を付けてください。

- 対象Node／画面、確認した現状、利用者が困る具体的な状況。
- 最小限の追加・変更案。既存デザインのどのComponentや表現を再利用するか。
- 優先度：実装着手前に必要／該当機能の完成までに必要／将来改善。
- 分類：未作成画面／状態不足／操作・遷移不足／整合性問題／表示・アクセシビリティ／API・データ依存。
- Figmaで先に確認すべきか、既存方針内の実装補完で足りるか。
- 対応しない場合の影響、他の画面・API・iOSへの影響。

不足の列挙だけで終えず、具体的な文言、必要な項目、状態遷移、簡単な配置案まで提案してください。目的がない新機能や画面を増やさず、完成済みの表現をできるだけ維持してください。新規領域の提案は歓迎しますが、必須の不足と分けてください。

## 4. 実装へ向けて作る計画

今回の分析に基づき、画面と状態をどのComponent・データ・APIへ対応付けるかを整理してください。技術構成は15の推奨を出発点とし、現在のコードと整合しない場合は理由付きで見直しを提案してください。承認済み技術だと決めつけず、パッケージのインストールは行いません。

最初の候補は「イベント1件を編集 → 複数枠・複数会場 → 下書き保存 → 再表示」です。ただし現在のFigma・実装状態から、先に共通Shellや認証・API契約を整える必要があれば依存関係を明示してください。

各実装単位に、対象Node・保持する見た目・必要な状態・実データ接続・完了条件・テスト・ブラウザでの比較方法を付けてください。静的な見た目の完成、モック上の操作、実保存・公開、iOS連携の完成を分けてください。

既存画面サイズでのスクリーンショット比較、文字切れ・重なり、主要フロー、失敗状態の確認を計画に含めてください。実装時には画面を画像として貼ることでUIを代替せず、操作可能な部品として再現します。

## 5. 変更・確認の境界

- 今回はFigma・コード・依存関係・DB・原本資料を変更しません。既存の決定案も上書きしません。調査成果物の新規作成は許可します。
- 起動時にDBを変更する既存APIが調査資料で指摘されています。画面理解のために既存環境で起動せず、必要なら起動処理を静的確認してください。
- デプロイ、commit／push、Issue・MR作成、認証設定変更、外部へのメッセージ送信は行いません。
- 秘密値や正式でないサンプルを成果物・本番データへ転用しません。
- 通常の読み取りや案の整理で、その都度確認を求めないでください。対象アクセス・重大な方針衝突などで判断が不可欠な部分だけ質問し、独立して進められる調査を続けてください。
- 完成済みFigmaを再承認させる一覧は作らず、「追加提案への判断」と「実装開始の対象範囲」を確認できる形にしてください。
