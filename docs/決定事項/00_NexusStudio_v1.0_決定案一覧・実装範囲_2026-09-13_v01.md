## 3. v1.0へ含める詳細案

| 領域 | 機能単位の案 | 実装できたと判断する代表条件 |
|---|---|---|
| Login・共通 | 認証、全管理者操作、保存・離脱・競合・取得失敗表示 | 直接APIも保護し、入力と公開結果を失わず扱える |
| Overview | 公開版、開催日、未公開変更、検証、最近の操作 | 古い結果・取得失敗・正式0件を区別する |
| Events | 1イベントに複数日・枠・会場、終日と参加案内、画像、中止 | 正しい日時と選択会場で公開・案内へつながる |
| Open Campus | 開催回と開催日、一般公開時間、日単位中止 | 関連イベントの時間・中止が整合する |
| カテゴリ | 名前・順序・新規選択停止・公開履歴 | 既存分類を保持しつつ新規利用を制御できる |
| Spots | ID・属性・位置・出典・参照・新規会場選択停止 | 名称変更でIDを変えず、経路を壊す位置変更を防ぐ |
| Map Data | 2D／3D、既存建物の頂点・高さ・階数、Spot配置 | 正式値を保持し、未編集レイヤーと経路を失わない |
| Validation | 全下書き診断と公開候補検証、修正導線 | 無関係な下書きを公開阻止の理由にしない |
| Releases | 確認した版の公開・取り下げ・履歴・復旧 | 部分反映と重複を防ぎ、現行参照で復旧を検証 |

各文書のIDは機能・項目・検証シナリオの追跡用。横断的な機能は複数文書に現れるため、単純なID合計を開発チケット数や工数として扱わない。

## 4. 今回の統合で明確にした境界

1. **公開する内容と参照情報の変更を区別する。** 通常のイベント公開では下書き1件全体。開催時間変更の際は公開中の内容を基準に終日枠の参照時間を再解決する追加案とし、編集中の説明を混ぜない。
2. **新規選択の停止と取り下げを分ける。** カテゴリ・Spotとも、既存公開参照を維持したまま新規割り当てを止められる案。初回公開する下書きは既存公開参照と扱わない。
3. **開催日の中止と枠独自の中止を分ける。** 親の日付を再開しても独自の中止を解除しない案。
4. **開催枠は所属開催回の開催日から選ぶ。** 開催日の参照不正は阻止、当日の一般公開時間外の時間指定は警告として確認する案。07 v02の期間外日付を警告とする記述はv03で見直した。
5. **Spot属性も地図の公開単位に含める案。** 地図全体が未完成ならSpot訂正も待つ制約が残る。イベント日時等の独立公開は維持する。
6. **描画と経路接続は別の完成条件。** ピン配置・輪郭編集・3D表示の成功だけで、入口や案内経路の正しさを証明しない。
7. **履歴と復旧を実装対象として分ける。** 過去版を参照できるだけでは復旧機能の完了ではなく、下書き保護・再検証・新しい公開まで必要。

07・08は項目と運用関係、09・10は位置と地図、11は共通の公開と復旧、12は共通UIを主な定義先とする。矛盾を発見した場合は確定事項を優先し、提案間の差を隠して実装しない。

## 5. 初期対象外とする案

確定済みの対象外は建物・道路の新規作成。それ以外は、次のものを初期対象外として提案する。

- 道路の形状編集、入口・Navigation Graphの直接編集、専用Indoor Editor。既存の必要データの保持・検証・導入手順は対象。
- 精密3Dモデル、屋根編集、外部3D背景を必須とする構成。
- 定期開催の自動生成、開催枠や項目単位の公開。
- 予約・定員・チケット・待ち列・リアルタイム混雑。
- 来場者分析を中心とするダッシュボード。
- 独立したMedia・Users／Permissions・汎用Settings、一般公開サインアップ。
- 汎用ファイル取り込みUI、CSV一括編集、カテゴリ階層、複雑な文章装飾。
- SwiftUI実行や実機を代替するPreview、Studioのスマートフォン編集UI。

対象外案をiOSのv1.0案内機能の削減へ転用しない。既存Adminに実装されていることも、自動的な採用理由にしない。

## 7. 実装・公開の前に必要な確認

| 確認対象 | 必要な根拠 | それまで進められる範囲 |
|---|---|---|
| 正式イベント・開催情報・カテゴリ | 供給資料と管理単位 | フォームと架空例の設計 |
| ID・Spot種別・階・座標系 | 正式台帳と既存契約 | 項目・検証・参照UIの設計 |
| 入口・経路・階層接続 | 実測と検証済みの接続情報 | 問題表示・導入・公開の設計 |
| 高さ・階数 | 正式値と出典 | 未確認状態を含む表示・編集設計 |
| 認証・管理者登録と復旧 | 現行基盤・運用方法 | Loginと期限切れ等のUI設計 |
| API・iOS・旧データ互換性 | 実装と既存データの読み取り調査 | 新旧の概念モデル比較 |
| 描画・編集技術 | 対応Geometry・費用・提供条件の検証 | 技術に依存しない操作設計 |
| 対象ブラウザ・性能・保持期間 | 代表環境・データ量・容量 | 検証シナリオと観測項目の設計 |

現地調査・正式情報・実機確認が必要な事項は、人の確認待ちとして管理し、推測で埋めない。個々の未確定値が独立した案書作成全体を止める理由にはならない。

## 8. 実装単位への分け方の案

| 段階 | 対象 | 完了条件 |
|---|---|---|
| 1. 契約確認 | 既存API・ID・配信・認証と新モデルの対応 | 互換性・移行・公開単位・検証対象を説明できる |
| 2. 編集基盤 | Login、一覧・フォーム、開催回・枠・会場、保存状態 | 下書きを壊さず作成・編集できる |
| 3. 地図編集 | 既存建物・Spot・出典・2D／3D・差分 | 元データを保持して編集と取り消しができる |
| 4. 公開基盤 | 検証・公開候補・履歴・復旧・競合 | 整合性と下書き保護のシナリオを満たす |
| 5. 利用者への反映 | iOS・配信・オフライン・中止／取り下げ | 正しい時間と目的地を同じ公開版で表示できる |

段階は開発の順序案であり、v1.0から後半を削除する意味ではない。初期稼働には編集だけでなく公開・復旧・配信の確認が必要。
