### 2.2 認証・登録・復旧の最小運用案

Identityの管理者IDと有効状態を持ち、全管理者にStudioAdmin policyを割り当てる。初期管理者追加・無効化・パスワード／MFA復旧は、運用者のみ実行できる管理コマンドで提供する。共有秘密や既存JWTをそのまま個別管理者の証拠にしない。登録endpointを一般公開せず、Identityの一括endpoint登録を無検討で採用しない。

Cookie期限・CSRF・ログイン試行制限・失効確認・MFA／回復コード・再起動時のData Protection鍵保持を実装する。登録済み管理者の一人が編集から復旧まで完結できる。サーバー運用者によるアカウント復旧は公開承認フローではない。認証期限切れ時は編集内容を保持し、再ログイン後に未完の公開を自動実行しない。

### 2.3 費用・保守

MapLibreはBSD-3-Clause、DrawはISCであり、ライブラリ自体の従量課金はない。PostgreSQLも別途DBソフトウェアのライセンス利用料を前提としない。いずれも必要なlicense表示を保持する。外部背景を必須にしなければ、地図表示ごとの有料API契約は不要（14のO05、O11）。

総運用費は「ホスト＋DB容量／バックアップ＋画像保存／転送＋ドメイン等」。現在のホスト契約・予算・アクセス量が未確認なので月額を捏造しない。初期は現在の既存サーバーで成立するかを評価し、追加サービスは容量・信頼性が不足すると分かった段階で比較する。ライブラリ無料と運用費ゼロは同じではない。

弱点は、.NET基盤更新とReleaseの新設、地図ライブラリの接続調整、画像を含むバックアップ運用が必要なこと。React／NodeでAPIも全て新設する案は、既存DBとC#契約の再実装が増えるため第一候補にしない。地図の代替はTerra Drawのみを有力候補として残すが、穴／Multi型保持の検証が先に必要。

## 3. データ構造の契約案

### 3.1 編集と公開の保存モデル

| 論理データ | 最小の内容・不変条件 |
|---|---|
| EventIdentity | eventId。既存GUIDを継承する場合は同一実体の移行記録を保持 |
| DraftHead | entityKind、entityId、draftRevisionId、basePublishedRevisionId、version。古いversionで更新不可 |
| ContentRevision | revisionId、entityKind／entityId、schemaVersion、payload JSONB、作成時刻・操作者、hash、原本来歴。作成後は不変 |
| RevisionReference | revisionId、参照種別、対象ID、slotId等の参照位置。payloadから同一transactionで作成する索引。索引だけを正にしない |
| MapRevision | 一つの地図全体の編集状態、原本参照、geometry、建物付随属性、Spot、保持レイヤー、Graph／floor等の参照。未対応情報も保持 |
| ReleaseCandidate | candidateId、baseReleaseId、選択したRevision集合、操作種別、派生影響、確認対象hash、検証器の版、検証結果、有効期限 |
| Release | releaseId、単調増加sequence、parentReleaseId、公開したRevision集合／manifest、配信schema、派生結果、時刻、操作者、操作ID。確定後は不変 |
| ActiveRelease | 対象環境／Datasetの現在releaseId＋version。公開確定時だけ条件付き更新 |
| Operation | operationId、actorId、Idempotency-Key、requestHash、状態、結果releaseId、失敗情報。重複公開防止と結果照会 |
| Asset | assetId、sha256、媒体形式、bytes、処理状態、保存先識別子、利用Revision。秘密付きURLを保存モデルにしない |
| AuditEntry | 操作者・対象・操作・版・結果・時刻。VisitLogとは別の管理操作ログ。秘密値は含めない |

初期はEventの共通情報と枠・会場を1つのRevision JSONに保存する。多数の可変テーブルを逐次更新するより「イベント全体の版」を扱いやすく、不完全な下書きも保存できる。検索用列・参照索引は別に用意する。全Revisionをイベントソーシングで再生する仕組みは初期不要。

### 3.2 Event draft payload

以下はフィールド契約案。正式データ例ではない。

| 項目 | 型・ルール |
|---|---|
| eventId | 安定したUUID。Spotのcanonical IDと別 |
| title／description | string。空文字の下書きを許容。公開時必須の詳細は正式運用で確定 |
| occurrenceId | 開催回IDまたはnull |
| categoryId | category IDまたはnull。初期は1つ案 |
| imageAssetId | 処理済みAsset IDまたはnull |
| slots | EventSlot[]。0件の下書き可 |
| slots[].slotId | 安定UUID。日時変更で維持、複製は新規発行 |
| slots[].dayId | 所属開催回の開催日IDまたはnull。別に自由入力日付を重複保存しない |
| slots[].timeMode | `timed`／`allDay`／未選択null |
| slots[].startLocal／endLocal | timedの場合のHH:mmまたはnull。同日内・JSTを初期案。allDayでは正の時間を二重保存しない |
| slots[].participationMode | `startAtTime`／`dropIn`／未選択null。allDayから自動決定しない |
| slots[].isCancelled／cancellationNote | 枠独自の中止・案内。開催日中止とは別 |
| slots[].venues | Venue[]。0件の下書き可 |
| venues[].spotCode | canonical IDまたは未選択null。GUID・表示名ではない。既知IDの大文字小文字保持 |
| venues[].note／order | 会場補足・表示順。同枠内の重複spotCodeを拒否 |

未入力nullと不正値を分ける。必須欄の空欄は保存できるが、壊れたJSON、重複slotId、構造上の不正、同枠内の重複会場、過大入力は保存エラーにする。参照先が未公開・未解決でも、識別可能な下書きとして保持し公開を止める。存在しないIDを勝手に補正・別IDへ変換しない。

公開projectionでは各枠に`startAt`／`endAt`をオフセット付きISO 8601で確定し、`timezone=Asia/Tokyo`、dayIdと参照Revision、timeMode、participationMode、effectiveCancellationとreasonSourcesを含める。allDayでも00:00〜24:00にせず、同じReleaseの公開開催時間を解決する。

### 3.3 開催回・カテゴリ・Spot・地図

- 開催回：occurrenceId、name、timezone、days[]。dayIdは安定、date、publicStartLocal、publicEndLocal、isCancelled、noteを持つ。初期は1日1連続区間。参照中の日付の直接変更・削除は止め、新日追加→イベント移行の手順を使う。
- カテゴリ：一覧単位のRevision。categoryId、name、order、selectableForNewUseを保持。停止後も既存の公開参照は表示する。
- Spot：既存GUIDは内部キー、spotCodeがcanonical ID。buildingId／floorIdは明示参照。位置のCRS・単位・出典・確認状態・案内到着点を区別。UIの新規Spot作成には内部draft IDを使え、正式ID未登録なら公開不可。
- 地図：全体の公開単位は維持。現行geometry Schema 1.0.0を基準にし、高さ・階数・出典・道路面・Spot等はversion付きの編集／付随属性契約として追加する。原本を公開Schemaに合わせて切り詰めた結果で上書きしない。
- 公開manifestはgeometry版、建物属性版、Spot版、Graph版、floor／案内版を同じMapRevisionから固定参照する。論理的な地図全体公開は複数ファイルでもよい。
- MultiPolygonは既存raw／編集モデルで保持できても、現行geometry v1へ変換して公開しない。必要な実形状が判明した時点でSchema改訂を明示し、iOSを先に対応させる。
- 高さ・階数はunknownを表せるnullable値。確認済み高さだけ3Dの正式押し出しへ使う。階数×仮階高、教室天井高からの推測は禁止。試験用の高さはPreview専用に隔離する。
- 公開済みcanonical IDは通常編集不可。既存E1-3に従い移行時はaliasと予約名前空間を整備する。台帳の`cr`／`rm`案を全室に自動適用しない。

## 4. 主要APIの契約案

パスは新設案。現在存在するAPIではない。管理系はすべてStudioAdmin policy、状態変更はCSRF検証を通す。旧`/admin/events`のPUT／publishをStudioの保存・公開には使わない。

| API | 要求・応答・意味 |
|---|---|
| `POST /admin/studio/events` | 空または入力済みdraftを作成。201、eventId、revisionId、ETag、保存時の問題一覧。operation keyで作成連打を防ぐ |
| `GET /admin/studio/events` | 一覧、公開状態／下書き状態／時刻、検索・ページング。取得失敗と0件を分離 |

| `GET /admin/studio/spots` | 名前・canonical ID検索、建物・階・公開版・新規選択可否。公開済みとdraft-onlyを明示 |

| `POST /admin/studio/release-candidates` | baseReleaseId、選択対象と固定Revision、操作種別を渡す。候補hash、派生影響、検証結果を返す |
| `GET /admin/studio/release-candidates/{id}` | 現在の処理状態・検証器版・有効性。エラーと未検証を区別 |
| `POST /admin/studio/release-candidates/{id}/commit` | Idempotency-Key、確認したcandidateHash、警告確認を渡す。202＋operationIdまたは確定結果。未確認のrevisionを公開しない |

Event取り下げはcandidateの`operation=withdraw`、復旧は`operation=restore`＋対象entity／過去Revisionで表す。専用の別公開パイプラインを増やさず、入力候補の作り方と検証規則を分岐する。通常publishの候補は選択したEvent draft全体を使用する。

エラーはProblemDetailsにcode、対象entityId、slotId、venueの位置、現行Revision、修正先を含める。400は構造不正、401／403は認証認可、409はID衝突・公開基準変更・キー内容不一致、412は編集競合、422は公開内容の不成立という案に統一する。404／410の公開終了表示は情報開示を考慮して統一する。

## 5. 選択公開・復旧の実装方式

### 5.1 一つの公開処理

1. active Releaseを読み、その公開参照集合を候補の土台にする。選択していない下書きをロード・結合しない。
2. 明示選択されたEvent Revision全体、MapRevision全体、開催回Revision、CategorySet Revisionを置き換える。新規依存が必要でも関連下書きを自動追加しない。
3. 同じ候補内で終日の実時刻と実効中止を再計算し、派生内容の差分を出す。表示名等も候補の公開参照から解決する。
4. schema、完全一致ID、会場・開催日・カテゴリ参照、素材ready、geometry／topology、必要なGraph接続、来歴、クライアント対応を検証する。検証サービス失敗は合格ではない。
5. immutable配信ファイルと画像を準備し、hash・サイズ・読取可能性を確認する。途中の生成物は公開URLにしない。
6. 短いDB transactionでactive Releaseのversionと選択Draftのversionを照合する。変わっていたら確定せず再検証・再確認へ戻す。必要なら対象行をロックし、検査直後の別保存との競争を防ぐ。
7. Release、Operation結果、AuditEntry、active pointerの更新を同一transactionでcommitする。公開側はpointerが指す不変集合だけを読む。
8. commit応答を失ってもoperationId／Idempotency-Keyから同じ結果を取得する。端末のタイムアウトを公開失敗と断定して二重公開しない。

画像ファイルの保存とDB commitを分散transactionにはしない。先に不変ファイルを完成させ、参照をDBで確定する。DB失敗なら未参照ファイルが残っても公開内容は変わらない。未参照ファイルの回収は猶予期間と参照検査の後に行い、公開中・下書き・履歴・復旧候補が使うものを消さない。

公開前の障害ではactive pointerを変えず、直前の公開版を維持する。commit後の応答欠落は「失敗」ではなく結果不明として照会する。commit後に配信基盤自体が故障した場合は、公開transactionの原子性とは別の可用性障害として扱い、監視・再配信・端末の旧版維持で対応する。

初期は全体active Releaseが変わったら候補を再検証する保守的な競合規則を推奨する。細かな依存version vectorは不要。無関係な**下書きエラー**で公開を止めない原則は維持するが、別の公開が同時に進んだ場合には再確認が必要になる。この操作コストは単独運用では許容しやすい。

### 5.2 特殊操作のルール

| ケース | 成立条件・保護 |
|---|---|
| 開催時間変更＋公開Eventに未公開説明あり | 公開Event RevisionだけからallDayを再解決し、新Releaseの配信projectionを作る。未公開説明のRevisionはそのまま。Event本文の部分公開UIは作らない |
| timed枠が開催時間の外へ出る | 勝手に時刻を変えない。差分・警告を確認する。dayIdが別開催回なら阻止 |
| 親の日付中止→再開 | effectiveCancelledを再計算する。slot.isCancelledは変更しない |
| 新規選択停止後の訂正 | 公開基準の同じEvent／slot／spotCode参照の維持だけを例外とする案。別slotへの複製は新規割当。カテゴリは同じEvent／categoryIdの継続で判定 |
| 取り下げ済みEventの再公開 | 公開中参照がないため新規利用条件で検証する保守的案。停止Spot等を特例で再利用しない |
| Spot取り下げと過去・中止枠 | 初期は公開中Eventの全枠を参照検査する。過去枠だから参照を消してよいと推測しない。表示だけ残す例外は後続契約に分離 |
| 復旧で停止カテゴリを復活 | 現在の参照と新規割当条件を検証。過去版なら全て許可する例外を作らない |
| 復旧時の下書き | draft headもpayloadも変更しない。公開baseが動いたことを示し、次の公開時に最新参照で検証。古いRevisionは履歴で参照可能 |
| 地図に問題があるがEvent訂正をしたい | 現在公開MapRevisionが有効なら訂正可能。未完成MapDraftを混ぜない。公開Map自体が既に壊れていれば、その事実を隠さず参照修復が必要 |

### 5.3 画像と履歴の保持

初期では公開中・保存下書き・復旧履歴が参照するRevision／素材を自動削除しない。未参照アップロードの期限・公開履歴の保持期間・容量上限は本番投入前に運用値として決める。無制限保持のまま長期運用する意味ではない。

イベント画像は1枚・任意。初期形式はJPEG／PNG／WebP等のiOS対応を確認して固定し、サイズ／画素数をサーバーで検査する。SVG・HTMLを画像として無条件に受け付けない。今回、具体的な容量上限や画像処理ライブラリの採用は未確定で、最初の下書き到達点ではimageAssetId=nullとして進められる。

## 7. iOSとの接続計画

### 7.1 データ取得・オフラインの契約案

manifestにreleaseId、sequence、schemaVersions、公開時刻、必要ファイルごとのhash／bytes、互換性条件を含める。地図・Spot・Graph・基本案内は同じ公開組合せで保存する。イベントにも絶対日時と日付を持たせ、HH:mmだけで今日かを判定しない。

端末は現在の版を使いながら新manifestを一時領域へ取得する。必須ファイルの取得・hash・schema・ID参照を検証し、保存を完了してからactive pointerを原子的に切り替える。ネットワーク失敗、checksum不一致、容量不足、非対応schema、強制終了では旧pointerを維持する。最初の同梱版がなければ未提供として表示し、fixtureで成功表示しない。

任意画像を必須更新の阻止要因にするかはmanifestで定義する。推奨は画像なしで読めるイベントを基本とし、地図・Spot・Graph・基本案内は必須。画像がないと成立しない内容を任意へ格下げしない。画像を旧Releaseと取り違えないようURL／hashを版に固定する。

更新は起動・foreground復帰・手動更新を基本案とし、currentにはETag再検証、不変版には長期cacheを使う。サーバーの現在版より古い応答を受け取ってもsequenceを逆戻りさせない。運用上の復旧も新しいsequenceのReleaseとして配信する。保存日時・公開日時・内容の有効日を区別して表示する。

### 7.2 実装対象

| 領域 | 変更点 | 合格条件 |
|---|---|---|
| 新ReleaseStore／通信adapter | URLSession、永続保存、active pointer、全画面共通snapshot | 画面間で別Releaseの会場・イベントを混ぜない |
| HomeClient／HomeModels | 複数枠を今日の日時へ整理。empty／failed／savedを維持 | 0件と取得失敗を区別。過去の保存版を今日へ置換しない |
| Event詳細・会場選択 | eventId／slotIdから枠・全会場を表示 | 複数会場では選択が必要。中止・終日・随時参加を区別 |
| AppRouteRequest／Coordinator | eventDetailsの単一Spot前提を緩和し、会場選択後にMapSelectionへ渡す | 選んだcanonical IDが完全一致で目的地になる |
| SearchClient／MapContentClient | 同じReleaseのSpot・カテゴリ・Eventを解決 | 同名異階をIDで区別。未知IDは代替しない |
| MapSurface／routeHandler | 検証済みMapDataset・Graphへの接続 | 手動出発地、屋外・屋内・階層間・屋内外接続の経路を端末内で計算 |
| 保存失敗時のView／Store | 以前の整合snapshotと更新失敗を同時表示 | HomeStoreの単純failed化で保存内容を失わない |

最初のiOS確認はSimulatorでできるが、実機の機内モード・再起動・容量不足・実際のGraph到達性は本番前に別途確認する。Studio Map Editorの範囲を狭くしても、iOS v1.0の経路・オフライン要件は削減しない。

## 8. 地図編集の技術検証計画

### 8.1 原本と編集stateの分離

原本JSONを不変保存し、ソースhash・feature index・source IDを記録した導入対応表を作る。MapLibre／Drawに渡すのは編集可能なgeometryと必要な表示属性のコピーのみ。編集完了時はallowlistされた差分を元の編集stateへ適用し、未編集Feature・未知属性・metadata・道路／入口／Graphを丸ごと保持する。

保存後は編集state全体を再読込し、未編集部分の構造比較とhash照合を行う。公開用CLIの14棟出力は配信projectionの一つであり、原本26地物やStudio編集stateを置換するファイルではない。

性能はまず代表PC・対象ブラウザ・実原本26地物で測定する。大量データfixtureは将来量に根拠がある場合だけ追加する。未測定のFPS・許容件数を達成値として置かない。
