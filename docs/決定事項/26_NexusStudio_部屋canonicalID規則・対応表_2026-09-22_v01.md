## 2. 採用する規則（D-22）

```
{building_id}_{floor_code}_{type}_{seq:03}
```

| 要素 | 規則 | 例 |
|---|---|---|
| `building_id` | E1-1 の14棟に限る | `mb`、`ptb`、`ctc_main` |
| `floor_code` | E1-2 と同一（`{n}f` / `b{n}f`） | `1f`、`2f`、`b1f` |
| `type` | 下表の閉じた集合 | `cl`、`cr`、`wc`、`rm` |
| `seq` | `001` から。`(building, floor, type)` の組内で一意。3桁固定（R-012） | `001` |

**`{building_id}_{floor_code}` は E1-2 の `floor_id` と完全に一致する。** したがって部屋IDは常に自分の `floor_id` を接頭辞として含み、既存 validator の接頭辞検査（`MapDatasetValidator.cs:99-100` と同じ方式）をそのまま適用できる。

### 2.1 型コード

| code | 意味 | 件数 |
|---|---|---|
| **`cl`** | 教室（classroom） | 8 |
| **`cr`** | 廊下（corridor） | 2 |
| `wc` | トイレ | 20 |
| `rm` | 上記以外の室（実習室・事務室・諸室など） | 44 |

`cl` と `cr` は **D-21 の指定どおり**。`wc` は原本で最も多く使われていた区分（14件）をそのまま残した。`rm` は残りをまとめる汎用区分である。

**型を追加する場合は決定記録を更新してから使う。** 実装側は閉じた集合として検証する。

### 2.2 既存の予約名前空間と衝突しない理由

| エンティティ | 形式 | 判別子 |
|---|---|---|
| 建物 | `{building}` | 型セグメントなし |
| フロア | `{building}_{floor}` | 末尾が `f` |
| 屋内ノード | `{building}_{floor}_**n**_{seq:03}` | `n` |
| 屋内辺 | `{building}_{floor}_**e**_{seq:03}` | `e` |
| 正式入口 | `{building}_**ent**_{seq:03}` | `ent` |
| **部屋・廊下** | `{building}_{floor}_**cl/cr/wc/rm**_{seq:03}` | `cl` `cr` `wc` `rm` |

型コード `cl` / `cr` / `wc` / `rm` は `n` / `e` / `ent` と重ならず、いずれも末尾が `f` でないためフロアIDとも区別できる。**単一の平坦な名前空間の中で機械的に判別できる。**

### 2.3 表示名は ID に入れない

室の用途・名称・番号は `name` フィールドに保持し、ID には入れない。E1-2 が同じ理由でノード・入口の命名から名称を排除している。

> 「ノードの用途、座標、接続順、施設名は ID に埋め込まない」
> 「**表示名や方角を含める（`mb_main_entrance`）**: 表示名・正式指定・方角の見直しで ID 変更が発生するため却下」（E1-2）

これにより、2A教室の名称が変わっても `mb_2f_cl_001` は不変でいられる。E1-3 の「一度公開した canonical ID は不変とする」を満たす。

2. **旧IDを `spot_id_aliases` へ登録する。** E1-3 が「IDを変更するときは、新しい canonical ID を発行し、旧IDを alias として残す」と定めている。対応表の `alias_required` 列は全行 `yes`
   - alias 登録時は `alias_code` が全 canonical ID と衝突しないことを検証する（§1 で確認済み：衝突0件）
3. **`Conflicts` シートの C-003・C-004・C-014 を「解消」へ更新する**（§3）
4. **MapDataset schema v1.1 に `roomFeature` を追加する**（6-5）
5. **`nexus-mobile/docs/decisions/E1-7-room-canonical-ids.md` として昇格させる**

`spot_id_aliases` テーブルは E1-3 で設計済みだが**未実装**であるため、2 の実行には実装が先に必要である（14 §4）。

## 8. 採用しなかった案

| 案 | 却下理由 |
|---|---|
| **旧IDの局所符号を保持する**（`mb_2f_cl_2a` のように `2a` を残す） | `ctc2_AKL_BNE` のように `_` を含む局所符号が機械的に解析できず、区切り文字の多義性が残る（§3-4）。E1-2 が同じ理由で名称由来の命名を却下している |
| **ID台帳の提案どおり教室を `rm` にする** | **D-21 が教室 `cl` を指定した。** また `rm` は「部屋一般」を指す汎用語で、原本の意味コード方式（`wc`／`gym`／`pc` 等）から外れる |
| **廊下を `cor` にする**（ID台帳提案） | **D-21 が廊下 `cr` を指定した。** 結果として廊下2件は改名不要になり、変更量が9件から7件へ減った |
| **調査Excelの `f2` 形式に統一する** | E1-2（採用済み決定記録）とスキーマの `floorId` 正規表現が `{n}f` を要求する。`floor_id` が部屋IDの接頭辞にならず、validator の接頭辞検査を流用できない |
| **階が不明な室に階を推測して割り当てる** | 製品方針が禁じている。**結果として推測は不要だった**（§4） |
| **全室を汎用の `rm` に統一する** | D-21 が教室と廊下の区別を求めている。また会場選択UIで種別が分かる利点を失う |
