# Nexus Studio 地図公開の入口と検証設定の判断記録

- 作成日：2026-11-01
- 版：v01
- 状態：**利用者が決定**（2026-11-01、質問への回答）。D3 の設定値そのものは未記入で、オーナーの記入と承認を待つ。
- 関連：Issue m0o9l0v3/NexusStudio#11、[29 v01](29_NexusStudio_M1地点表示の判断記録_2026-10-24_v01.md)（M1-D4・M1-D5）、nexus-mobile E2-5 §3.3・§5.4、`docs/implementation/issue-18-map-dataset-validator.md`

## 1. 背景

29 M1-D5 で地図を公開対象に加えると決めたが、Studio には地図（`studio.map_datasets`）を作る経路が無い。Map Data の画面は Figma Phase 2 が未作成のため、CLAUDE.md の方針で構成の確認前に作れない。また、公開判定（`MapDatasetValidator` の公開モード）には、キャンパスの範囲や距離の許容値など、地図だけでは決まらない承認済みの値が要るが、その値はどこにも定められていない。

## 2. 決定事項

| # | 論点 | 決定 | 補足 |
|---|---|---|---|
| D1 | 地図を Studio に入れる経路 | **管理コマンドで取り込む**（`dotnet run -- map import --file …`）。検証器に通して下書きの版を作り、公開は既存の Release（対象の種類 `map`、29 M1-D5）で行う | 参照データの `reference import` と同じ考え方。画面は Map Data の構成確認の後 |
| D2 | 地図が一度も公開されていないときの Spot の公開 | **公開を止める**（29 M1-D4 をそのまま適用）。地図と Spot を同じ公開操作で出すか、地図を先に公開する | 位置の分からない地点を参加者向けに出さない。bundle に `placement: null` は出ない |
| D3 | 公開判定の承認済みの値の置き場所 | **2つに分ける。** キャンパス全体の値（範囲・ENU 原点・入口と経路の距離の許容値・出発ノード）は `deploy/map-validation/approved-settings.json` に置き、Git でレビューする。地図の版ごとの根拠（経路の所要時間・フロアの座標変換の検証結果）は取り込み時に GeoJSON と一緒に渡す | ファイルは `status: draft`・値はすべて null で作った。オーナーが記入して `approved` にするまで地図は公開できない。開発チームは値を作らない |

## 3. 後続

- オーナーが `approved-settings.json` の値を記入・承認する（`deploy/map-validation/README.md` の表）。→ 2026-11-01 に `startNodeIds` 以外を承認。`startNodeIds` は経路データ（nexus-mobile #16・#39）の作成後に記入・承認する。
- 地図の取り込みコマンド（版ごとの根拠の形式を含む）と、地図の公開対象（設定ファイルの SHA-256 を公開確認と結び付ける）。→ 取り込みは PR #20、公開対象は PR #21 で実装（`deploy/map-validation/README.md` の C）。
- `delivery` への bundle の射影。→ 移行 `AddParticipantBundles` と公開処理での射影（E2-5 §3.3）を実装。参照データの取り込み（`reference import`）が公開した Spot では bundle を作らない（次に Studio で spot か地図を公開したときの bundle に含まれる）。
- bundle の不変条件（E2-5 §5.3）と建物名の食い違い（O-1c）の検証。→ 組み立てた bundle を `ParticipantBundleInvariants` で確かめ、破れていれば公開前の確認で `bundle_invariant_violated`（公開阻止）、公開処理では例外でトランザクションごと取り消す（Release も残らない）。建物の Spot の名称と同じ ID の `building.properties.name` が違えば `building_name_differs`（警告。Spot の公開時と、公開中の建物の Spot がある地図の公開時）。条件5は受け手の規則、条件6は配信表の主キーとトリガーで保証する。
