## 1. 目標と範囲

管理者が開催日ごとの正しい時間を登録し、イベントで再利用できるようにする。開催時間の訂正時は、関連する終日イベントの時間も整合した状態で公開する。カテゴリはイベントを探すための分類として管理する。

イベントの個別公開、登録済み管理者による編集から公開までの完結、複数枠・複数会場、終日・随時参加への対応を前提とする。学校全体の行事管理、予約、リアルタイム混雑管理へは範囲を広げない。

## 2. 開催情報の構造案

| 単位 | 持たせる情報 | 意味 |
|---|---|---|
| 開催回 | 安定したID、名称、開催日一覧、管理情報 | 1つのOpen Campusとして管理するまとまり |
| 開催日 | 安定したID、日付、一般公開の開始・終了、開催状況、中止案内 | 終日イベントが時間を参照する単位 |
| イベント | 対象の開催回ID | 初期案は1イベントを1開催回へ関連付ける |
| 開催枠 | 対象の開催日IDと時間方式 | 終日は開催日の時間を使い、時間指定は固有の開始・終了を持つ |

- 1開催回に複数日を登録できる。連続日であることを必須にせず、日付の一覧として保持する。
- 名前・日時が変わってもIDは維持する。別の開催回を作る場合は別IDにする。
- 同じ開催回の同じ日付を二重登録しない。異なる開催回が同日であることだけでは禁止しない。
- 一般公開時間は初期案として1日1つの連続区間。日本時間を明示し、開始より後の終了を必要とする。
- 開催枠の日付は選択した開催日から決まる案とし、日付と参照先が食い違う入力を許さない。
- 選択した開催回にない日で企画を行う場合は、開催日を追加するか所属先を見直す。期間外の自由な日付を警告だけで公開するv02の案は、こちらの案では採用しない。
- 一般公開時間の前後にある時間指定企画は、予定として必要な場合があるため警告で確認する案。終日は一般公開時間そのものを使う。
- 日をまたぐ開催、複数キャンパスの異なる時間帯、1日の複数の一般公開区間は必要性を確認して追加判断する。

### 情報の出典

開催名称・日付・時間・カテゴリ名の正式値は提供資料から登録する。画面設計用の架空値を初期の公開データにしない。管理者向けに出典名／URLと確認日を任意記録する案とし、事実確認の担当や運用は別途整理する。公開のために別人の承認を要求する仕組みにはしない。

| OC-06 | 開催日の変更・削除 | 参照イベントを確認する。参照中の日付を無確認で変えたり消したりしない |
| OC-07 | 関連イベント一覧 | 開催回・日ごとにイベントと開催枠を表示する |
| OC-08 | 影響対象の抽出 | 終日枠、時間指定枠、公開中、下書きのみを分けて示す |

| OC-12 | 開催回の公開 | 開催回を単位として確認・公開する案。関連する公開データも整合させる |
| OC-13 | 開催日の中止 | 日単位で中止と案内を設定し、関連イベントへの影響を確認する |

公開に必要な名称・開催日・時間が不足している場合は保存まで可能とし、公開時に阻止する。開催回は日付から予定前／期間中／終了を表示できるが、公開状態・中止状態とは別に扱う。非連続の日付では、最初と最後の日付の間をすべて開催中と判断しない。

## 4. 画面案

一覧は開催回ごとの表とし、選択後は中央に基本情報と開催日、右側に関連イベント・検証結果を表示する。初期の画面配置案であり、最終デザインではない。

```text
開催回名　公開中・未公開変更あり
                                   ［下書き保存］［公開内容を確認］
開催日                             影響するイベント
  9月20日 10:00–16:00               終日イベント：公開中／下書き
  9月21日 10:00–15:00               時間指定イベント：確認対象
  ［開催日を追加］                  ［関連イベントを見る］
```

例示の日時は正式データではない。時間変更後は「終了16:00 → 15:00」「終日イベントの終了も変更」のように影響を明示する。未確認の件数を画面上の正式な数値として捏造しない。

## 5. 終日イベントを伴う時間変更の公開案

### 通常の流れ

1. 開催日の時間を編集して下書き保存する。この段階ではイベントの公開時刻を変えない。
2. 公開確認で、対象日にある公開中の終日イベントを抽出する。
3. 開催情報の変更と、終日枠の実際の時間がどう変わるかをまとめて表示する。
4. 公開済みのイベント内容を基準として、新しい開催時間から終日枠の実際の時間を解決する。イベントの編集中の説明・会場等は混ぜない。
5. 対象全体を検証し、開催情報と影響するイベントの整合した版をまとめて公開する。失敗したら従来の組み合わせを維持する。

### イベントの下書きが残っている場合

公開済みイベントの「終日」という指定が参照する時間を更新する案とする。イベント下書きから特定の項目を抜き出す操作は設けない。確認画面で公開に使う基準が「現在の公開内容」であることを示し、イベント下書きは保持する。

これはv02で未確定だった参照先変更の公開方式の提案であり、イベント1件内の部分公開を利用者に開放するものではない。手入力された共通情報・開催枠・会場を変更して公開する通常操作は、イベント1件全体を引き続き対象とする。

下書きがあるイベントでは、後にその下書きを公開するとき、最新の開催時間を参照して差分を再計算する。古い開催時間へ暗黙に巻き戻さない。対象のイベント内容や参照元が確認後に変わった場合は再検証・再確認する。

### 影響対象ごとの扱い

| 対象 | 時間変更時の動作 |
|---|---|
| 公開中の終日枠 | 実際の時間を確認対象へ含め、一緒に反映する |
| 未公開の終日枠 | 自動公開しない。次回の編集・公開確認で新しい時間を示す |
| 時間指定枠 | 時刻を自動変更しない。一般公開時間の外になる枠は警告する |
| 中止済みの終日枠 | 中止状態を維持して参照時間を更新する案。更新前の内容は履歴に保持する |
| 別日・別開催回・無関係な地図下書き | 公開対象へ含めず、無関係なエラーで阻止しない |

新規の開催回と新規イベントを最初に公開する際は、開催回を先に公開し、続いてイベントを公開する簡単な手順を初期案とする。未公開の終日イベントを検出しただけでは公開へ追加しない。

### 開催日変更・削除・中止

- 日付変更：終日の時間変更と異なり、イベントの開催日を動かすため、初期は参照がある日付の直接変更を阻止する案。新しい開催日を追加し、関連イベントの全体を確認して移す。旧日付の無参照を確認して整理する。
- 削除：下書き・公開版から参照されている開催日は削除を阻止する。開催中止の案内を削除で代用しない。
- 中止：その日に属するイベントの実効的な開催状況にも反映し、時間指定枠も通常開催と表示されないようにする案。イベント独自の中止は残す。
- 開催日の中止を解除しても、独自に中止した枠を通常へ戻さない。中止理由の参照元を区別する。
- 公開済み開催回の取り下げは、関連イベントを孤立させるため、初期は独立操作として提供しない案。中止案内と、イベントの取り下げを使い分ける。運用上必要なら関連データの一括取り下げを別途設計する。

## 6. カテゴリ管理案

カテゴリは、イベントの内容による分類として扱う。開催日・建物・学科・参加条件などを無計画にカテゴリへ詰め込まない。正式なカテゴリ名・必要な種類は未確認のため、本書では候補名を登録済みデータとして作らない。

### 初期の情報と公開単位

- 安定したカテゴリID、表示名、表示順、新規選択に利用できるかを保持する案。
- イベントはカテゴリIDを1つ持つ案。複数カテゴリは必要性を確認して追加判断する。
- 名前を変えてもIDは維持する。意味が別の分類へ変わる場合は新しいカテゴリを作る。
- カテゴリ一覧をひとまとまりの公開単位とする案。保存だけで公開名・並び順を変更しない。
- イベントの分類変更はイベントの下書き変更として扱い、イベント単位で公開する。
- カテゴリの表示名・表示順の公開は、そのカテゴリを参照する公開済みイベントの表示にも反映する。Previewと差分で影響を示し、関係ないイベント下書きを公開しない。
- 「新規選択を停止」は、既存の公開イベントから分類を消す操作とは分ける。停止後も既存参照の表示を維持し、訂正・再公開を妨げない。新規イベントへの割り当ては阻止する案。
- 下書きで停止カテゴリを以前から参照しているだけでは既存公開での継続利用とは扱わない。初回公開時は利用可能なカテゴリへ変更する。
- 参照中カテゴリの物理削除・分類の自動一括置換・階層カテゴリは初期対象外案。

### 機能一覧

| ID | 機能 | 操作・結果 |
|---|---|---|
| CAT-01 | 一覧・参照確認 | 名称・順序・利用状態・参照イベントを確認する |
| CAT-02 | 作成 | 正式な名称に基づいて新しいカテゴリを下書き作成する |
| CAT-03 | 名称変更 | IDを維持し、公開名との差分と影響を確認する |
| CAT-04 | 並べ替え | 上下ボタン等で順序変更し、キーボードでも操作する |
| CAT-05 | 新規選択の停止・再開 | 既存参照を保持しながら、新規割り当ての可否を変更する |
| CAT-06 | 保存・検証・公開 | カテゴリ一覧の差分と参照影響を確認して公開する |
| CAT-07 | 履歴確認・復旧 | 過去版を確認し、現在のイベント参照と検証して復旧する |

独立したSettings画面を必須にせず、Events内の「カテゴリ管理」から開く案とする。登録済み管理者は操作でき、別の権限管理画面は追加しない。

## 7. 検証・公開整合性

| ID | 判定 | 条件と対応 |
|---|---|---|
| OV-01 | 公開阻止 | 開催回名・開催日・一般公開時間が不足、または時刻の関係が不正 |
| OV-02 | 保存／公開阻止 | 同じ開催回内の開催日重複、ID重複、不正な参照形式 |
| OV-03 | 公開阻止 | イベントが存在しない開催回・開催日、別開催回の日を参照する |
| OV-04 | 変更／削除阻止 | 参照中の開催日の直接の日付変更・削除 |
| OV-05 | 確認を促す | 時間変更後、時間指定枠が一般公開時間の前後へはみ出す |
| OV-06 | 再確認 | 確認後に参照時間、影響イベント、公開の基準版が変更された |
| CV-01 | 公開阻止 | カテゴリ名が空、ID不正・重複 |
| CV-02 | 確認を促す | 表示名が重複して選択を誤りやすい |
| CV-03 | 公開阻止 | イベントが未公開・存在しないカテゴリ、または新規割り当て不可のカテゴリを新たに使用する |
| CV-04 | 復旧阻止 | カテゴリを過去版へ戻すと現在のイベント参照が欠ける |

イベント公開時には、カテゴリと開催情報を含む公開後の組み合わせを検証する。開催情報・カテゴリの公開側からもイベントへの影響を検証する。必要な公開データの組み合わせを端末へ提供し、異なる版を混ぜない配信契約を別途設計する。

公開処理の部分反映、重複実行、結果不明時の誤表示を防ぐ要件はイベント管理と共通とする。復旧も現在の参照を検証し、関連イベントの日時やカテゴリが破綻する過去版への切り替えは行わない。

## 8. アプリ・Overviewへの連携

- 開催回名と実際の開催日を表示する。開催日間の空白日を開催日と誤認させない。
- 「今日」の表示は日本時間の実日付と公開済みの開催日を照合する。開催がない日を直近の開催日に勝手に置き換えない。
- 情報取得の失敗、公開情報0件、過去の保存情報を使う状態を区別する。
- 時間変更・中止の反映は配信・キャッシュ更新と合わせて検証する。オフライン端末への即時反映を保証しない。
- カテゴリ名や順序を更新しても、安定したIDによって既存の分類との関係を維持する。
- カテゴリの新規選択停止は管理側の操作であり、それだけで来場者向けの分類や既存イベントを隠さない。
- 開催日中止とイベント独自中止を組み合わせた表示、解除時の挙動をiOS側と合わせる。今回の文書作成でiOS変更を行うものではない。

## 10. 残る判断と実装前の確認

- 開催回の実際の区切り、正式な開催名・日付・時間・カテゴリの供給元。
- 一般公開時間を1日1区間とする案で足りるか。日またぎの必要性。
- カテゴリを1つ選択にする案で足りるか、正式候補と並び順。
- 参照時間を更新する公開方式と、イベント下書きの差分再計算・競合検出の具体設計。
- 開催日中止の連動と、開催回自体を取り下げる機能の必要性。
- 開催情報とカテゴリを新たな公開単位にするためのAPI・配信・Releaseの拡張。
- 過去情報・公開履歴・復旧候補・下書きの保持期間。

本書はイベント管理v02の未確定事項を具体化する案。開催枠の日付選択、親の開催日中止の反映、参照時間の更新方式を採用する場合は、イベント詳細案の対応箇所も次版で統合する。過去版を確定仕様として併用しない。

次の細分化対象は、イベントが参照するSpotsの一覧・検索・属性・座標編集と、地図公開の具体的な境界とする。
